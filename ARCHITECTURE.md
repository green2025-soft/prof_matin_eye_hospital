# Application Architecture

## Contract and current state

[AGENTS.md](./AGENTS.md) and this document define the contract for a reusable Laravel modular boilerplate. Build the foundation before project-specific work. The application uses Blade, Bootstrap 5, HTML forms, and session authentication on the `web` guard. Project instructions take precedence over conflicting examples in reusable skills.

Laravel 13 is installed at the project root on PHP `^8.4.1`, with Vite, Bootstrap 5, Popper, Font Awesome Free 7.3.1, and an admin dashboard. `nwidart/laravel-modules` 13.0.0, `spatie/laravel-permission` 8.3.2, and `spatie/laravel-multitenancy` 4.2.2 are installed with module Composer merge integration. Three approved modules, Core, TenantCore, and Hospital, are registered with functional providers. Laravel Boost, Pint, Pail, Collision, and Tinker support development.

Core Admin, TenantCore User, and Hospital Doctor inherit shared Account behavior and authenticate through the sole `web` session guard. Admin/User roles and the common Doctor permission set use the same native `web` permission guard and existing current-database permission IDs; Doctors have no individual permission assignments, role assignments, or owner-role bypass. Admin uses the central connection; User and Doctor use the selected tenant connection. Doctor profile and credentials live wholly in `doctors`, without a `users` row or user-link FK. Shared account/session/permission migrations remain reusable. The foundation includes authenticated dashboards, password recovery, isolated tenant databases, explicit setup/adoption/migrations, tenant/account/access management, plans/subscriptions, invoicing/payments, checkout, and grouped settings. Preserve application keys, credentials, and database data. Further workflows need requirements; source implementation does not establish a successful live merchant payment.

The starter uses file sessions/cache and a synchronous queue. The health route requires no database; tenant host resolution needs the installed central registry. `APP_TIMEZONE=Asia/Dhaka` controls application time. Installation/provisioning/deployment commands explicitly create or migrate the intended database; requests and provider boot never do this work.

## Modules and ownership

Keep the approved modules at the project root, alongside Laravel's `app/`; further modules require explicit name/scope approval:

| Module | Owns | Boundary |
| --- | --- | --- |
| `Modules/Core` | Platform administrators, tenant/domain registry, shared account schema, tenancy/setup, plans/subscriptions/billing, settings, shared auth/views/helpers | Independent of concrete TenantCore classes |
| `Modules/TenantCore` | Tenant User model, account operations, Branch, Payment Type, and Division/District/Thana CRUD, read-only Audit Logs, shared module chooser/landing views, and tenant-only schema | Implements Core's TenantAccounts boundary |
| `Modules/Hospital` | Hospital routes/menu, Refund Cause and other catalogs, Patient/Doctor CRUD, Appointments, Consultations, Patient Investigations, Patient Operations, Refunds, and Due Collections | Tenant-wide catalogs and branch-owned patient, doctor, and clinical records; shared landing remains provisional, dedicated dashboard deferred |

Keep business structure unspecified until project requirements exist; do not invent additional feature modules or model hierarchies. Keep contracts with the module that owns the capability; Core receives only contracts that are genuinely shared infrastructure. Use explicit public operations across boundaries, avoid circular dependencies, and do not write directly to another module's tables.

The selected scope is full SaaS. Core owns platform administrator identities, the tenant/domain registry, and financial records in a central database. Each tenant has its own database; TenantCore owns its users and permission data. Preserve the existing first tenant's account; the platform administrator is a separate identity. Credentials belong in operator-managed secrets, not source or seeders.

Spatie's automatic finder is disabled. `ResolveApplication` resolves trusted central hosts or active registered tenant domains after boot and invokes native tenant switching; unknown/inactive tenant domains return 404. The native database task runs before the application settings task, which scopes cache/permissions/storage and selects the default connection. Resolve before cookies/sessions; verify session scope immediately after StartSession and before authentication. Keep the context until middleware termination so exception rendering, streamed responses and response collectors see the correct identity; then restore central state and reset web managers.

The public guard remains `web`, with Laravel's unchanged SessionGuard and context-qualified session/remember-cookie names. Core defaults to TenantCore User authentication on tenants and Admin centrally. `Services/CachedUserProvider.php` extends Laravel's `EloquentUserProvider` only for cached GET/HEAD session-ID restoration; credential, remember-token, and customized provider queries keep native database reads. Only enabled Hospital registers its configured `Services/HospitalUserProvider.php` adapter, Doctor provider/password broker, and additional login type; Core consumes generic registered type metadata and has no Doctor imports or table queries. Explicit User/Doctor selection delegates to configured native Eloquent models, retaining numeric User IDs or `doctor:<id>` in native guard session/remember values without email fallback. With Hospital absent or disabled, native User login/recovery remains the default. Host-only cookies and tenant-session checks preserve context isolation. Platform handoff remains short-lived, single-use, and tenant/domain-bound. Resolve and authorize before `Tenant::execute()`; pass explicit values and do not reuse another tenant's models or actor gates inside it. Native execution restores prior context on failure.

TenantCore's provider registers `ResolveBranch` after sessions/authentication and before bindings; Core does not reference concrete tenant classes. Actual tenant Branch records provide branch choices independently of `has_branches`; selection is mandatory only on opted-in route groups. A tenant Account's (User/Doctor) `branch_id` assignment overrides session selection and disallows chooser/switch writes. Unassigned users select any current-tenant branch with POST `/branch-dashboard/{branch}` and clear it with DELETE `/branch-dashboard`, both protected by CSRF. Session `branch_id` and `branch_user_id` bind selection to the tenant/Account; provenance uses `getAuthIdentifier()` so numeric Users and `doctor:<id>` remain distinct; each request verifies that provenance, resolves the branch through its current-tenant context snapshot, and clears stale selections. Mutating requests reload branch state from the database. Unknown bound branches return 404. The topbar displays the branch name and permits switching only for unassigned users with a selection.

Global resolution is optional: existing Users/Roles/Permissions/Settings/Billing/Branch/Audit Logs and Division/District/Thana management work without selection and retain their tenant-wide queries. Tenant root redirects to `/module-dashboard`; module selection and TenantCore's `/workspace` remain branch-free. Hospital resource pages and `/hospital` landing use `branch:required`: missing selection opens the existing branch chooser when branches exist and resumes the intended Hospital page after selection. Catalog selectors use separate authenticated-tenant-only routes without branch selection. Assigned users use their valid fixed branch automatically. With zero branches, root/module selection and TenantCore remain accessible while Hospital stays blocked until a branch is available. The provider's opt-in `branch:required` alias uses the same `ResolveBranch`; its private resolver caches trusted `active_branch`/`branch_id` request attributes once per request, avoiding repeated queries when global and route middleware both run. Branch-owned route groups must use that alias, filter reads by trusted `branch_id`, and assign ownership server-side on writes; Patient, Appointment, Consultation, PatientInvestigation, PatientOperation, Refund, and DueCollection opt into Hospital BaseModel behavior for this. The alias does not automatically scope queries. Keep genuinely unscoped features, authentication, Billing recovery, and chooser routes outside required-branch groups; recovery and chooser also remain outside subscription restrictions.

Native tenant-aware queues retain tenant identity; a tenant job must also enforce lifecycle eligibility. Central jobs explicitly implement Spatie `NotTenantAware`: the installed package rejects default-aware jobs without a tenant ID. Database session storage and queue transport/batches/failures are pinned centrally, while cache and uploaded-file locations use the active context. File sessions/cache and sync queues remain the configured development defaults.

## Installation and schema changes

`platform:install` explicitly creates/claims the central database, applies central/shared migrations and creates the platform owner. `tenant:create` registers a tenant, allocates a server-generated immutable database name/token, claims that database, applies the shared/tenant schema and creates its owner. `tenant:adopt` explicitly attaches an existing database and preserves its owner/password. A failed setup retains its registration; `tenant:retry SLUG` resumes it with the original ownership token (`--adopt` for adoption). Active/suspended tenants cannot be reprovisioned. Core invokes tenant account operations through the owner-defined contract rather than writing tenant users directly.

`platform:install`/`platform:migrate` initialize missing central settings and the free Starter plan, synchronize permissions, and enroll existing active/suspended tenants only when a subscription is absent. Tenant setup and `tenants:migrate` initialize tenant settings; successful provisioning enrolls the free plan before activating the tenant. Existing settings, subscriptions, credentials, and account passwords are preserved. Default enrollment never creates a paid invoice or charges a customer.

Tenant forms generate a unique slug from the workspace name and suggest `{slug}.{TENANT_BASE_DOMAIN}`. The primary local platform uses `localhost:8000`; the default tenant suggestion is `workspace.localhost`, and tenants cannot claim a central host. The base defaults to the central host's parent or the host itself when it has no dot; production can set `TENANT_BASE_DOMAIN=example.com`. Domains remain editable, and edits preserve existing values unless explicitly changed. The profile includes optional address/phone, a strict PNG/JPG/WebP/GIF logo up to 2 MB, and the boolean `has_branches`; the flag does not create branch records. Logos use generated central public-disk paths, retain the old image on failure, and clean replaced/unreferenced files.

Database ownership uses a metadata marker bound to the application key and central/tenant token. Existing foreign markers are never overwritten. An unmarked populated database requires explicit adoption. Keep the application key stable; key rotation requires an explicit marker rotation/recovery procedure. An interrupted claim with an empty metadata table requires operator repair rather than automatic takeover. A MySQL advisory lock serializes schema work for each database. Provisioning/adoption never drop databases; permanent deletion is a separately authorized central workflow.

`BaseController::destroy()` delegates Tenant Delete to the existing `TenantProvisioner`, requiring a central owner or `tenants.delete`, CSRF, and the custom irreversible confirmation. Under the database advisory lock, run `DatabaseInstaller::verifyTenantDeletion()` protected-database and UUID/HMAC ownership preflight before lifecycle changes; refusal leaves tenant/subscription state unchanged. Refresh access/authorization and commit `DELETING` plus subscription cancellation, then `dropOwnedTenant()` repeats verification immediately before DROP outside the central transaction. Central/system databases and foreign markers are refused; active online checkouts must resolve first. Remove scoped local/public/cache files and the logo, then central records in FK order: checkouts, payments, invoice items, invoices, subscriptions, domains, tenant last. Pending manual submissions and financial history are intentionally purged. Keep plans, the global invoice counter, and platform accounts. On partial failure retain the deleting registry/token for Delete retry, accepting an already absent database; block edits, reprovisioning, new checkouts, and subscription changes. Shared session/queue entries may expire or fail closed; this is not a blanket purge of global history.

Migration paths are declared once in `config/multitenancy.php`: root infrastructure plus Core `database/migrations/shared` and `central` for the platform; shared schema plus TenantCore and Hospital `database/migrations` for tenants. The optional tenant-only directory is included when present. Existing migration filenames remain unchanged so adoption preserves applied history.

Hospital's Investigation Category migration has an explicit tenant migration path in `config/multitenancy.php` and uses `tenants:migrate`; providers never migrate. Add further module paths explicitly when actual tables are required; do not introduce boot-time directory scans.

The three new TenantCore geography migrations create empty Division, District, and Thana tables parent-first, then insert a pinned subset of local `bangladesh-geocode-master` JSON: 8 divisions, 64 districts, and 494 Upazilas explicitly approved as Thanas. Each embeds only original IDs, names, Bangla names, parent IDs, and the full source MIT license; inserts add timestamps in chunks of at most 200 on the tenant connection. No runtime external path or new seeder/data files are needed. Existing tenants receive pending migrations through `tenants:migrate`; new tenants use the same portable initial data. Applied migration history prevents repeat imports and preserves later CRUD edits.

Add each table/column change as a new native Artisan migration in the owning path; never edit a migration already applied to a real database. `php artisan tenants:migrate` skips `deleting` tenants and lazily visits the other registered tenants, including active/suspended/failed records, verifies ownership and applies pending migrations on its own connection. Each database has its own `migrations` table. New tenants use those same paths and receive the latest schema. Use `--tenant=ID_OR_SLUG` for selected tenants, `--pretend` for a preview and `--force` in production. Digit-only selectors mean IDs. A failure is reported with its tenant ID, other tenants continue and the command exits unsuccessfully; fix and rerun to apply the remaining migrations. There is no transaction spanning separate databases and no automatic rollback. Use forward fixes and staged nullable/backfill/constraint migrations for populated tables. Never run `migrate:fresh` against real tenant databases.

For the explicit local Hospital exception, the existing `2026_10_27_135801_create_operations_table.php` and `2026_10_25_171930_create_investigations_table.php` definitions were changed to plain decimal amount columns without a new migration/file. Both installed tenant schemas were reconciled under ownership/advisory locks by converting historical integer amounts exactly as old value / 100 before removing the old columns. Recorded create migrations do not rerun, so older external databases need explicit reconciliation; future ordinary schema changes still use new migrations. `commission_percent` remains `DECIMAL(5,2)`.

## Subscriptions, billing, and settings

All plans, subscriptions, invoices, payments, and checkout attempts are central records. Tenant billing policies restrict access to the current tenant; platform financial actions require their separate abilities. Manual payment entry asks only for Invoice ID and Amount received; its hidden replay key is system-generated. PaymentController prepares form/receipt data; PaymentService handles saving and settlement. Financial records have no generic delete workflow; explicitly confirmed permanent Tenant Delete intentionally purges that tenant's financial records. Money uses integer minor units and explicit decimal conversion, never floating-point calculations.

Plan and Setting use the ordinary Controller/Model/Request/View/Route flow without a resource service. Plan owns exact price conversion; `PlanRequest` keeps the default Starter slug fixed, its price zero, and its active flag enabled. `PlanPolicy` prevents deletion of the default or referenced plans. Manage plan route access separately at `/core/plan-permissions` through its own controller/requests and shared persistence; ordinary plan edits preserve it. Plan `route_permissions` are an additional limit on mapped tenant actions: `null` allows all and `[]` allows none; account roles/policies still authorize each action. Login/password recovery, home, and Billing recovery stay outside that plan limit. A subscription snapshots price, currency, and monthly/yearly interval. A free plan may change immediately; an already usable paid period must finish before a plan change. Trials are not repeatedly granted. Paid periods require settled invoices; free renewals do not create charges. Cancellation can end access now or at period end.

`Subscription::forTenant(Tenant)` loads the plan for eligibility and feature checks. `AccountService` calls `SubscriptionService::createUser(Tenant, Account, Closure)` to hold the central subscription row lock while counting the configured primary User model and finishing its tenant account transaction. Doctor records do not count toward this User quota and currently have no count limit. Do not replay that cross-database callback through an outer transaction retry. There is no separate subscription-access forwarding service. Substantial subscription lifecycle, provisioning, invoicing, access mutation, and checkout/settlement workflows retain services.

Invoice forms offer Draft or Issued; saving Issued requires issue authorization and finalizes the invoice. The due-date field uses bundled Flatpickr in the shared JavaScript/CSS and submits `Y-m-d`; its Request still validates the value. Requests validate and calculate line amounts/totals; issuance preserves financial snapshots. Paid/partially paid states derive from recorded payments. Unnumbered invoices display `Invoice #ID`; issuing a legacy unissued invoice preserves recorded money and derives its payment status. Subscriptions produce one invoice for a billing period, and settlement is idempotent. The platform Invoices page includes pending manual payment review; tenant Billing remains separate, with no platform Billing page. Manual submission records a reference, not a settled payment; approval records settlement and rejection leaves accounting unchanged. Checkout snapshots invoice principal plus a fixed extra charge, verifies that gross amount, and credits only principal to the invoice. Payment records/receipts retain the charge separately, and replay must match it. Historical receipts do not reactivate cancelled or elapsed periods.

SSLCommerz, bKash, Nagad, and EPS use the shared gateway contract. Providers start disabled; operators supply merchant credentials and select the correct environment. Persist encrypted, hidden credential snapshots for outstanding checkout verification. Settle only after server-side verification matches the stored order/reference, amount, and currency; neither a redirect nor a submitted status proves payment. Production rejects sandbox settlement. Live testing requires actual merchant credentials and a publicly reachable HTTPS `PAYMENT_CALLBACK_BASE_URL` pointing to the canonical central application; local build/lint success is not live-payment evidence.

Settings use fixed grouped singleton records in each active database. `config/settings.php` owns metadata/defaults and `SettingRequest` validates/normalizes input; the model persists validated values and encrypted credentials. `Setting::values(group, connection)` merges defaults and saved values; gateway readers explicitly use central. Tenant groups are company/branding/general/email/hospital; SMS is central only. Branding accepts strict PNG/JPG/WebP/GIF logos up to 2 MB and PNG/ICO favicons up to 512 KB, stored with generated names on the current scoped public disk. Requests reject supplied paths; the controller preserves old files on failure and deletes replaced files after commit. Central Payments uses fixed Manual/SSLCommerz/bKash/Nagad/EPS subbuttons and loads one selected provider record per request. Individual gateway records/secrets remain separate; manual defaults enabled with instructions, and every provider has a fixed two-decimal `extra_charge` defaulting to `0.00`, never a percentage. Save/errors preserve the provider; legacy group/edit URLs select that tab. Missing rows initialize through existing `platform:migrate`/`tenants:migrate` without new schema. Blank credentials preserve hidden saved values and are never flashed. Read current-plane logo/favicon URLs and branding in `LayoutComposer`, never during boot.

Email settings default disabled and fall back to deployment `MAIL_MAILER` (default `log` when unset). Enabled SMTP uses host/port, `tls` for STARTTLS, `ssl` or `none`, and sender address/name; encrypted username/password may be blank for unauthenticated SMTP. Laravel's registered `workspace` transport resolves settings through `WorkspaceMail` on first send, never at boot; tenant/request/job context changes reset cached mailers and sender state. Central `Sms::send()` uses the configured GET/POST API URL, JSON/form format, sender ID, and encrypted credentials/header/parameter JSON templates with `{to}`, `{message}`, `{sender_id}`, `{api_key}`, `{username}`, and `{password}` replacements. There is no public send UI; operators must map their provider, interpret its response, and use an adapter for signed/OAuth flows. HTTP 2xx is not proof of delivery.

Laravel schedules the native `GenerateDueInvoices` job hourly to maintain due subscriptions and invoices. The Invoices Generate Invoices action dispatches the same workflow; manual maintenance remains `subscriptions:sync --force`. `payments:reconcile --force` runs every five minutes to recheck outstanding gateway attempts. Run Laravel's scheduler each minute in production. These operations never automatically debit a customer.

## Module layout and wiring

Use the standard `nwidart/laravel-modules` layout:

```text
project-root/
|-- app/
|-- Modules/
|   |-- Core/
|   |-- TenantCore/
|   `-- Hospital/
|-- resources/
|-- routes/
|-- composer.json
`-- package.json
```

Module PHP lives in `Modules/{Module}/app/` with `Modules\{Module}\...` namespaces. Routes, views, migrations, and seeders use lowercase `routes/`, `resources/views/`, and `database/` paths. Root Composer configuration merges `Modules/*/composer.json`; keep module metadata, namespaces, providers, and `modules_statuses.json` consistent. Register module routes, views, and migration paths once through their owner. Simple CRUD declares an explicit model permission prefix and uses shared gates and target resolution; business-specific policies use native model attributes, and already-bound models remain supported.

Use native `php artisan module:make ModuleName` for an explicitly approved module, replacing `ModuleName` with its approved name; the name argument is required. Do not hand-scaffold a module. Core, TenantCore, and Hospital already exist, so do not rerun creation or use `--force` on them; another module requires an explicitly approved name and scope. `php artisan module:list` inspects registration.

The configured generator supplies a lean skeleton: `module.json`, Composer namespace mapping to `app/`, a functional provider using native `loadRoutesFrom()`, and lowercase `routes/web.php`. Its empty route group declares `web`/`auth` middleware, the kebab-case module URL prefix, and the lowercase module route-name prefix ending in a dot. Add controller groups inside it when actual routes share a controller. It does not generate fake controllers/views/models/resources, a separate frontend, APIs, tests, or factories. Register views and schema when their actual files are added, and reuse the Core layout. This skeleton does not implement a complete authorized CRUD; resource work still follows the shared recipe below.

Tenant root defaults to `/module-dashboard`, independently of branch selection; a user's custom local redirect remains respected. `/workspace` (`tenantcore.dashboard`) retains the tenant overview, while platform root is unchanged. TenantCore's `ModuleDashboardController` and `module-dashboard` views provide both chooser and shared landings using native `Module::getOrdered('desc')` and each enabled module's `tenant_dashboard` metadata. Core has no tenant metadata; TenantCore and Hospital declare their cards. Permissioned cards require role authority and a usable plan's route permission. Metadata never replaces route authorization: Hospital resource pages and GET `/hospital` have `auth`, `tenant`, `subscribed`, `branch:required`, and `permission:hospital.view`, also mapped in Plan Permissions; catalog option routes are separate and require only authenticated tenant context. New approved modules declare metadata and their own authorized named route; no custom scanner/catalog layer is needed. The fixed Modules navigation item uses scalar composer data. The current Hospital landing is provisional; its dedicated dashboard is deferred until its features are completed.

TenantCore's authoritative primary User remains `Modules/TenantCore/app/Models/User.php`; Hospital owns its separate `Doctor` authentication/profile model. Both inherit Core Account and use guard `web`. `/users` always targets the configured primary User model, even when an authorized Doctor performs account administration. Core reads generic `loginType()` metadata for reset-link identity and `profileRoutePrefix()`/`profileUpdatePermission()` for the correct account-menu edit route, without importing Hospital. Do not duplicate either tenant identity under root `app/` or another module.

TenantCore's Branch is ordinary CRUD at `/branches` inside the subscribed route group, with separate role and plan permissions. Name/address are required; `mobile_no`, `telephone_no`, email, and a raster logo up to 2 MB are optional. The tenant `branches` migration runs through `tenants:migrate` for existing tenants and the same migration paths for new tenants. Its thin controller uses shared persistence without a Branch service. The branch chooser reuses the model query contract for paginated search cards and the Core layout/styles.

TenantCore also owns the approved Administration catalogs at `/divisions`, `/districts`, and `/thanas`, tenant-wide without branch selection. Each has `name` and `bn_name`; District requires `division_id` and Thana requires `district_id`. Division names are globally unique within the tenant; child names are unique within their parent. Separate `divisions`, `districts`, and `thanas` `.view/create/update/delete` role/plan grants apply. Each uses six new resource files (Controller, Model, Request, migration, index, shared form), `$inlineForm = true`, and stable name/ID ordering through shared CRUD. Fixed menu links reuse existing scalar permissions. No resource Policy, service, provider, or composer changes are needed; parent reference hooks and restrictive foreign keys prevent referenced deletion.

TenantCore's Audit Logs at `/audit-logs` is a read-only Administration feature with native index/detail routes, `audit-logs.view` role/plan access, and a model-declared policy that checks tenant actor/context/database and denies writes. All current-tenant logs are visible with a searchable Branch selector, event, shared Flatpickr date filters, and actor/record-name search; no branch selection is required. The owned `tenantcore.audit-logs.branches` route is registered before resource detail binding and reuses `Branch::optionRecords()` for fixed-20 escaped prefix search under authenticated tenant context only, including assigned users; Audit Logs list/detail role and plan checks remain independent. Only the selected option is preloaded; logged branch-name links retain historical deleted-branch choices from the latest audit snapshot. Nullable branch context retains branch-free actions. Actor and branch IDs/names are historical snapshots without foreign keys; `actor_type` (`users`/`doctors`) distinguishes overlapping IDs and retains historical User attribution. The model also refuses saving/deleting, and details render escaped old/new JSON. Eight files provide AuditLog Model, Policy, Request, Controller, one tenant migration, AuditLogger, and index/show views. The existing tenant migration path gives each new tenant an empty audit table.

The substantive `Modules/TenantCore/app/Services/AuditLogger.php` registers native model/authentication events once through the existing TenantCore provider; this is shared infrastructure registration, not a per-resource CRUD entry. It captures created/updated/deleted events for Core BaseModel, Account, and Role families on the active tenant database with an authenticated tenant Account actor (User or Doctor), plus login/logout. Central, console, and provisioning actions are skipped. Spatie permission events are enabled for native role/permission attachment/detachment deltas. AccountService and RolePermissionService retain their serialized locks and apply only current-versus-desired grant differences with native remove/assign/revoke/give operations; unchanged grants produce no events. CurrentDeviceLogout is included as logout for tenant handoff device logout. An explicit safe-value allowlist, hidden-field exclusions, recursive secret-key redaction, and value-free secret-change markers keep credentials and raw request payloads out of logs. Direct audit inserts use the same tenant connection and surrounding transaction, avoiding recursive events and retaining rollback behavior. Bulk query-builder/raw SQL/counter writes and session-only branch chooser changes are not model events; earlier actions are not backfilled. Core remains independent of concrete TenantCore classes, and no new helper, layer, API, or config file is introduced.

Hospital's first approved CRUD is Investigation Category at `/hospital/investigation-categories`: Controller/Model/Request/View/Route plus its migration and shared authorization, no resource policy or service. Business fields are `name` and integer `ordering` (0–65535), with default ordering then ID. Categories are tenant-wide and shared across branches, with no `branch_id`; Hospital's branch-required route group still gates entry. Native resource actions map to separate `investigation-categories.view/create/update/delete` permissions in Role and Plan Permissions. Category overrides the intrinsic `hasReferences()` hook using its loaded investigation count or an existence query; common delete authorization uses it alongside the restrictive foreign key. Its read-only options require only authenticated tenant context. The category-specific page has a left inline form (Name before Ordering) and right list, using only `index` plus the shared `form` fragment; native authorized create/edit GETs render the same page, without a separate create page or New Category navigation button. Category declares `$inlineForm = true`; the shared BaseController defaults it to false. The base private `formValues()` builds common metadata once, and its private `form()` selects the standard page or inline index. Private methods are not extension points: no child form/getData overrides or private-parent calls. Typed index/store still delegate only to `listData()`/`saveData()`; protected `formData()` remains the existing hook for resource-specific values where needed. The index create form may be null when creation is forbidden; authorized edit still shows its populated form. List queries run only with `viewAny`; otherwise records are null, so write authority never exposes the list. Views use a generic `form` array or null, not `categoryForm`; no extra service, repository, or class is needed.

Operation Category at `/hospital/operation-categories` follows the same ordinary CRUD and `$inlineForm = true` pattern: Name before Ordering in the left form, with an authorized list on the right, and no service. Its unique `name` and integer `ordering` (0–65535) form a tenant-wide catalog with no `branch_id`, ordered by ordering then ID. Native actions use separate `operation-categories.view/create/update/delete` grants in Role and Plan Permissions under the Hospital entry gate. Its model declares `$crudPermission = 'operation-categories'` and uses shared authorization without a separate OperationCategoryPolicy. Its read-only options require only authenticated tenant context; intrinsic `hasReferences()` and the restrictive operations foreign key prevent referenced deletion. Its new table migration uses the existing Hospital tenant migration path and `tenants:migrate`.

Doctor Departments at `/hospital/departments` uses Hospital's `Department` model and `departments` table, with Doctor Departments as its page/menu label. Fields are required unique `name` (max 255), optional `description` (max 2000), and required integer `ordering` (0–65535, default 0); default sorting is ordering then ID. It follows Category's inline left form/right list through `$inlineForm = true`: unauthorized creation has a null form, authorized editing populates the shared form, and list data is null without view authority. Departments remain tenant-wide without `branch_id`, under Hospital's branch-required entry and separate `departments.view/create/update/delete` role/plan grants. Its six initial files are Controller, Model, Request, create migration, index, and shared form. A later additive migration introduces ordering without editing the original create migration already applied in both tenants; six initial files remain the pattern for future ordinary resources. Shared CRUD gates and existing route/config/menu files provide the wiring; no resource Policy, service, or per-resource provider/composer change is needed. Department lookup requires only authenticated tenant context; its reference hook plus restrictive FK prevent deleting referenced departments.

Doctor CRUD at `/hospital/doctors` keeps profile and credentials entirely in tenant `doctors`, without a User row or `user_id` link. Its shared create/edit form contains exactly the original 20 fields: English/Bangla name, specialist, BMDC registration, education degree, and current employment, plus Mobile No., Designation, Department, Gender, Blood Group, Address, Picture, Consultation Fee, Follow-up Fee, and Pad Footer Text; Email and Password are the only added fields. There are no role, permission, or password-confirmation fields on CRUD, and Doctors have no role or default `dr` role. The compact form uses four/two/one responsive columns, adjacent bilingual fields, and two-row textareas. Fees use `DECIMAL(20,2)`/`decimal:2` with default zero; pictures accept strict PNG/JPG/WebP/GIF up to 2 MB. Doctor extends Core Account with tenant connection, native hashing and the shared tenant Doctor permission set, not Hospital BaseModel. ## Responsibilities and request flow

| Layer | Responsibility |
| --- | --- |
| Routes and middleware | Web/session behavior, authentication, and consistent access requirements |
| `BaseController` and thin leaves | Shared HTTP actions, prepared view data, redirects; leaf model and resource declarations |
| `BaseRequest`, resource requests, `ListRequest` | Shared target/operation authorization and validation; resource-specific write rules and declared list-query rules |
| Service, where needed | Owning module's business rules, orchestration, and transactions |
| Model with `HasCrudContract` | Owned data/casts/relationships, write allowlist, intrinsic facts, safe fields, and query declarations |
| Model's `HandlesModelQueries` trait | Shared execution of constraints, search, filters, sorting, includes, selection, eager loading, and numbered pagination |
| Blade and shared partials | Direct escaped HTML fields using prepared values and common heading/table/action markup |

Keep business rules and queries outside Blade. Ordinary CRUD uses the shared controller and model directly, without a service. PatientService handles reusable patient writes and transactional ID allocation; DoctorService owns the separate Doctor identity/profile, picture, and shared-permission workflow; ClinicalEntryService owns the common clinical aggregate transaction, price snapshots, and financial calculations. Reserve other services for substantial multi-record, access, audit capture, provisioning, subscription, invoice, or payment workflows; they receive explicit values/context and return results rather than HTTP responses. Avoid forwarding layers.

Keep models limited to fields, casts, relations, safe query/display metadata, and intrinsic facts. Aim for roughly 40 lines per resource model where practical. Remove unused or duplicate responsibilities; do not compress code or create traits/services just to meet a line count. Controllers use the protected `formData(Account, Model)` hook for form choices/defaults; models do not prepare page/form data.

HTTP field validation and normalization belong only to Requests. Services consume validated payloads; CLI commands use native prompt validation. Do not duplicate `Validator` calls or field-format rules in models/services. Transactional state/accounting invariants, authorization, and authoritative gateway verification remain necessary workflow behavior. Existing substantial workflows may supply prepared values through the controller's form hook; this is not a reason to add a CRUD service.

Use descriptive singular/plural names, small focused methods, and explicit inputs/results. A reader should be able to follow validation, authorization, query construction, persistence, and response without discovering a hidden dispatch convention. Prefer clear branches and named operations over clever one-liners, application-level reflection/name guessing, or generic forwarding pipelines. Comments explain non-obvious constraints rather than narrating obvious code.

Prepare the display/query data needed by a page outside the template. Use explicit safe fields for forms, listings, and exports; do not expose secrets through model serialization or old input. Allowlist client-controlled search, sort, filter, and related-record selections before constructing queries.

The structure follows the Hrm reference's thin-resource/shared-parent flow, adapted to Blade/session authentication: resource controller → `BaseController` → model, and resource request → `BaseRequest`. Leaves declare model/resource metadata and provide typed `index()` → `listData()` and `store()` → `saveData()` delegations so Laravel resolves the native Form Requests. The base shares create/edit/destroy, form preparation, and redirects. Core's concrete `AccountController` serves both `/core/admins` and `/users`, resolving the model through the trusted authentication provider; there are no AdminController/UserController wrappers. Define route-prefix derivation once in `BaseController::routePrefix()`: the trusted matched name `core.accounts.edit` yields `core.accounts`. Leaves do not declare duplicate prefix properties or inherited action bodies, and updates need no wrapper.

`BaseRequest` shares action authorization, trusted bound-record/update resolution, and uniqueness support. Resource requests declare protected `$rules`, overriding `rules()` only for actual differences; `payload()` maps validated input when needed. `ListRequest` consumes the selected model's declarative query rules. Ordinary `BaseController` persistence calls `writeTransaction(actor, operation)`, locks/reloads the target, authorizes with the callback actor, fills the safe payload, and saves. Uploads require an explicit input-to-column mapping and directory; generated paths stay server-owned, native `afterRollBack` removes new files, and `afterCommit` removes replaced/deleted files from the captured scoped disk. The shared model trait defaults to its own database transaction. Role explicitly selects `AccessManager::transaction()` to lock the owner role and refresh the actor before target locking; its CRUD needs no RoleService. Plan/Role policies refuse protected or referenced deletions, with authorization rechecked against the fresh locked target. List counts avoid per-row relation queries. Role retains permission-cache invalidation after commit. Plan and Role controllers prepare their form values through `formData()`; models do not supply form data.

Write rules describe creation once. On ordinary partial updates, the base changes top-level `required`/`present` rules to `sometimes`; supplied child values still validate normally. Requests for complete submissions set `partialUpdates=false` to retain those requirements. `unique()` ignores only the trusted bound record, and `onCreate()` expresses create-only fields or optional edit passwords. Omitted partial-update values preserve stored data; checkbox markers distinguish keeping a selection from explicitly clearing it.

Models declare their query contract once through `HasCrudContract::queryContract()`:

- `$queryConstraints` defines server-owned read constraints, such as Role's `web` guard. Native model connections preserve the selected database boundary.
- `$searchable`, `$filterable`, `$filterableIds`, `$sortable`, and `$defaultSort` allowlist query behavior. Tenant's status filter uses the model's single `STATUSES` map. `$filterableIds` defaults empty and explicitly maps GET names `filter_doctor_id`/`filter_patient_id` to `doctor_id`/`patient_id`, keeping filter old input/errors separate from writes. Declared filters use nullable positive-integer rules and qualified equality, with pagination/page-size retention.
- `$exposed` is the explicit safe column list; an empty or invalid declaration fails. `$listColumns` defaults to that list and may declare an actual subset. Write fillable/validation fields remain separate.
- `$listWith`, optional `$formWith`, `$allowedIncludes`, `$exposedRelations`, and `$exposedCounts` declare related query/display data. Form eager loading defaults to the list declarations. Avoid model-wide `$with`.

`HasCrudContract` reuses `HandlesModelQueries` on the model itself. `queryRules()` supplies query metadata to `ListRequest`; `paginateRecords()` and `prepareForForm()` execute queries and load form relations without a repository. Validation runs in the Request. Queries apply model-owned constraints, safe fields and hydration/order keys, eager loads/counts, grouped escaped prefix search, and declared filters/sorts/includes. Native numbered pagination defaults to 10 rows and allows 5/10/15/20/30/50/100 plus `all` (displayed as All). All returns every filtered, authorized record on page 1 through the same query; changing size also resets page 1. Validate page/size, retain filters/sorting/size in links, and order deterministically with a primary-key tie-breaker. Unknown identifiers never become SQL columns or relation names.

Catalog AJAX selectors reuse inherited `BaseController::options(SelectorRequest)` and `optionRecords()`: server-declared exposed result fields (ID/name by default), escaped search with prefix matching by default and explicit `$containsSearch` opt-ins, deterministic ordering/ID, and fixed-20 `simplePaginate` with `pagination.more`, without COUNT/full preloads. Controller `$selectorFields` may include relations already declared in the model's `$exposedRelations`; `optionRecords()` separates scalar SQL columns and uses `with()` for each relation's declared columns. Native serialization keeps nested relations such as `category: {id, name}`. The existing AJAX iteration reads `category.name`; do not add per-resource mapping/flattening or a separate category-name `pluck()`. `SelectorRequest` checks only authenticated current-tenant Account context; User and enabled-module identities may read the registered choices without CRUD grants, plan/subscription access, or branch selection. Owned option routes use `web`/`auth`/`tenant` outside protected resource groups. Models carry no selector permission metadata, and no extra selector Gate/service is needed. HTTP never chooses a model/table/column. Shared Select2 assets debounce requests by 250 ms and preload only the selected option, with no MutationObserver or per-page assets. Resource CRUD checks remain unchanged; native BranchPolicy chooser/fixed-assignment abilities still govern actual branch switching.

Geography, Hospital category/department, Patient, Doctor, Investigation, Operation, and Audit Logs Branch lookups all use that authenticated-tenant-only contract. The shared `HasCrudContract::selectorFilters()` accessor also covers Account/Doctor models. Server-owned selector filter metadata still permits District `division_id` and Thana `district_id`; shared AJAX parent attributes filter children and clear descendant selections. PatientRequest independently validates the selected geography chain on create/partial update, including bail rules and existing geography values for omitted fields. The read-only catalog endpoint does not grant authority to create/update/delete any resource.

Intrinsic rules stay on their owning models: `Tenant::STATUSES`, `isReady()`, and `statusOptions()` describe lifecycle choices; `Role::OWNER_NAME`, `isReserved()`, and `Account::hasOwnerRole()` describe the reserved owner role. Policies and services consume these facts instead of repeating their literals.

| --- | --- | --- |

Use Laravel session authentication on the `web` guard and `spatie/laravel-permission` with that same guard. Core's `SessionController` handles login/logout HTTP responses; `LoginRequest` validates and normalizes credentials and attempts authentication through the configured guard. It does not reference a concrete TenantCore model. The `role`, `permission`, and `role_or_permission` middleware aliases are wired. Enforce policies/gates server-side for every action; Blade checks provide presentation feedback in addition to those checks.

`PasswordController` and `PasswordRequest` use native brokers and the shared root `auth` forgot/reset form. Broker `admins` uses central records and `users` uses the primary tenant User provider/token table. Enabled Hospital registers the Doctor broker and isolated `doctor_password_reset_tokens`; Core selects brokers from generic registered login-type metadata. Tenant forms and reset links preserve the validated User/Doctor choice, so overlapping emails cannot mix identities or tokens. Host context resolves first, submissions remain rate-limited, and normal link responses use generic existence wording. General text/phone fields have no generic five-character minimum; password rules retain `auth.password_min_length`, currently 5. Reset mail uses active Email settings or deployment fallback; the log transport does not deliver email.

Role CRUD edits names only; saving a name never changes grants. The separate `/core/permissions` workflow selects a visible role and displays grouped permissions from the current database. `PermissionController` reuses `BaseController`: its typed index passes service-prepared `pageData()` into `listData()`, its store delegates to `saveData()`, and its redirect hook retains the selected role. Scope resource lists to authorized records. Registered catalog selectors expose only fixed ID/name choices in the current tenant to authenticated Accounts, independently of resource grants. Writes still validate related IDs and ownership, and assign ownership through trusted logic.

Regenerate after privilege changes; invalidate the session on logout and regenerate the CSRF token. Use safe authentication failures and password hashing, and exclude secrets from flashed input, logs, and errors.

Apply rate limits at routes through middleware aliases. Core registers the named `login` limiter once and the login POST uses Laravel's built-in `throttle:login` alias: five submissions per minute per trusted scope/normalized email/IP, including successful and validation-failed submissions. ## Database integrity and performance

Use foreign keys, uniqueness constraints, indexes justified by actual queries, and transactions for related writes. Use row locks or atomic updates where concurrent actions could violate an invariant. Use explicit mass-assignment rules and persist validated/mapped fields; ownership, calculated values, and workflow status come from trusted logic.

Use parameterized queries. Billing uses integer minor units with two-decimal input/display conversion through `Money`; reject excess precision instead of silently rounding. Eager-load relationships consumed by pages and paginate unbounded lists. Batch or chunk large operations as appropriate; avoid global eager-loading or table splitting without a concrete read pattern that justifies it.

Every list follows the same query contract:

- Start with the authorized visibility/ownership scope, then apply grouped search and allowlisted filter/sort identifiers. User input never becomes an unchecked SQL column or expression.
- Filter, order, count, and paginate in the database. Do not call `all()`/unbounded `get()` and then filter or paginate in PHP. Select needed display columns plus primary/foreign keys required to hydrate relationships; eager-load relationships/counts used by the page.
- Use the shared numbered-pagination contract: default 10 rows, allowlisted sizes 5/10/15/20/30/50/100 or All, validated pages, and deterministic ordering with a unique tie-breaker. All intentionally returns the full filtered, authorized result on page 1. Retain validated filters and size in links; measure deep-page, total-count, and full-result costs on representative data.
- Keep query counts from growing per displayed row. Check small and full pages, and inspect timings/query plans at representative table sizes and common filters. Choose indexes around those predicates/orderings, including composite order and write costs, rather than indexing every column.
- Cache only when a real repeated read benefits and each writer has a clear invalidation responsibility. Bulk work uses bounded chunks, `lazyById()`/`chunkById()` where changing rows require stable traversal, or a job when duration/retry requirements justify it; do not queue ordinary small requests automatically.

Numeric page sizes bound the response; All intentionally loads the full authorized result. Record representative query counts/timings and address observed bottlenecks before promising an improvement.

Development enables Laravel's native lazy-loading prevention. Due Collection and Refund lists eager-load their source invoices first, then one Patient batch through the read-only computed `source_patient_id`; no patient data is copied into display wrapper arrays or persisted through that computed key. Their form previews read their own required records without loading unrelated list relations. Clinical list balance queries restrict their source and ledger aggregates to the current page's invoice IDs.

Public Branding values use the native `branding` file-cache store for 300 seconds, keyed by resolved connection and database. Transactional reads bypass that cache; native committed Setting saves/deletes invalidate the captured owning key. Selected Branding forms reuse their already-loaded Setting, and Billing reuses the subscription already read for that request.

`Modules\Core\Services\ContextCache` persists encrypted JSON attribute snapshots in the dedicated fixed-path `context` file store for GET/HEAD requests: session actors with roles/permissions, tenant/domain mappings, branches, subscriptions with plans, and Doctor shared permissions. Keys include the resolved connection/database; reads hydrate independent models rather than retaining serialized model objects. Owning model saves/deletes and native Spatie role/permission events invalidate affected groups after commit, capturing the original database across tenant switches. Bulk writes explicitly invalidate their affected group; rolled-back writes preserve the existing snapshot. The 900-second expiry is a fallback. Mutating requests and reads while any database transaction is open bypass the cache; credentials, remember tokens, and customized provider queries retain native reads. Access and financial writers reauthorize fresh locked records, and subscription usability evaluates the current time even when attributes came from cache.

Keep the boot path lean: providers register required behavior without database queries, network I/O, or custom directory scans beyond package discovery. Composer's optimized autoloader is enabled. Use production config/event/route/view caches only after environment setup and keep ordinary development uncached. Measure comparable repeated requests through the HTTP kernel before reporting a boot-time or response-time improvement.

Write services use the connection that owns the affected central or tenant data. Database, filesystem, queue, and external-service operations do not share one atomic transaction; tenant provisioning uses recoverable lifecycle operations across these boundaries.

Keep failures observable and user-safe. Distinguish validation/domain refusals from unexpected infrastructure failures; do not display SQL, class names, credentials, or stack traces in production error pages. Preserve intentional deletion and retention behavior through explicit requirements rather than importing another project's lifecycle rules.

Calendar dates round-trip as `YYYY-MM-DD`; datetimes use a consistent timezone convention. Prepare formatting through shared helpers/components when reuse warrants them, and keep PHP/database date boundaries consistent with the application timezone.
