# Project Guidelines

These instructions apply to this workspace. [ARCHITECTURE.md](./ARCHITECTURE.md) defines the application structure and coding conventions.

## Current Application and AI Tools

- This is a reusable Laravel 13 modular boilerplate at the project root on PHP `^8.4.1`, with Blade, Bootstrap 5, Popper, jQuery, Font Awesome Free 7.3.1, and Vite. Use Bootstrap; do not add Tailwind. Font Awesome core/solid styles are bundled locally through Vite.
- `nwidart/laravel-modules` 13.0.0, its Composer merge integration, `spatie/laravel-permission` 8.3.2, and `spatie/laravel-multitenancy` 4.2.2 are installed. Exactly two modules exist: Core owns platform/shared infrastructure and the tenant/domain registry; TenantCore owns `Modules\TenantCore\Models\User` and tenant account operations through Core's `TenantAccounts` contract.
- Native Spatie tenant switching selects a separate database per tenant. Core's Admin uses the central database; TenantCore's User uses the selected tenant connection. Both inherit shared Account behavior and use the public `web` guard. The foundation includes login/logout/password recovery, context isolation, explicit setup/adoption/migrations, tenant/account/access management, plans/subscriptions, invoices/payments, checkout, and grouped settings. Project-specific business workflows remain unspecified; live gateway verification requires operator credentials and reachable callbacks.
- Preserve the existing `.env`, application key, credentials, and database data. File sessions/cache and a synchronous queue remain the development defaults. The health route needs no database; tenant domain resolution requires the installed central registry. Database creation and migration run only through explicit installation/provisioning/deployment commands.
- Apply the bundled [Laravel fullstack skill](./.agents/skills/laravel-fullstack-development/SKILL.md) and [Laravel best practices](./.agents/skills/laravel-best-practices/SKILL.md) when relevant. Project instructions override their generic Vue/API/JWT, tenancy, and hierarchy examples.
- Keep `.agents/skills/` and [.codex/config.toml](./.codex/config.toml) with the project for portable native skill discovery and Laravel Boost MCP. Do not depend on a username, drive, or global plugin cache. The receiving PC still needs Codex and the application's runtime dependencies.
- Boost-generated guidelines are disabled; testing and Tailwind skills are excluded through [boost.json](./boost.json) and [config/boost.php](./config/boost.php). Preserve these decisions when updating Boost.

## Architecture

- Build one modular Laravel web application with Blade, HTML forms, Bootstrap, and session authentication on the `web` guard.
- Keep exactly two modules at the project root: `Modules/Core` and `Modules/TenantCore`, alongside Laravel's `app/` directory. This boilerplate foundation comes before project-specific work.
- Create an explicitly approved module with native `php artisan module:make ModuleName`, supplying the required name; inspect modules with `php artisan module:list`. Do not hand-scaffold modules or regenerate/force-overwrite the existing Core and TenantCore. Adding another module requires an explicit change to the current two-module scope.
- Use the standard `nwidart/laravel-modules` layout: module PHP code in `Modules/{Module}/app/` with `Modules\{Module}\...` namespaces; module routes, views, migrations, and seeders in lowercase `routes/`, `resources/views/`, and `database/` paths. Keep each module's `composer.json`, `module.json`, providers, and registration consistent.
- Keep the configured generator lean: module/Composer metadata, a functional provider using native `loadRoutesFrom()`, and lowercase `routes/web.php` with one `web`/`auth` middleware/module URL prefix/route-name prefix group; register views/schema when added and reuse the Core layout. Module creation supplies a skeleton, not an authorized CRUD feature. Do not generate fake controllers, views, models, resources, frontend builds, APIs, tests, or factories; actual CRUD work follows the recipe below.
- Core owns platform/shared infrastructure and must not depend on concrete TenantCore classes. TenantCore owns the tenant-facing foundation and the authoritative User model. Integrate through owner-defined contracts when a real boundary requires them.
- Laravel authentication selects Core's Admin for trusted central hosts and TenantCore's User for active registered tenant domains. Keep both on guard `web`; retain Laravel's native SessionGuard with context-specific session and remember-cookie names. Do not duplicate either identity model.
- Keep project-specific business structure unspecified until requirements are available. Do not invent business feature modules or additional model hierarchies.
- Keep contracts with their owner; place genuine shared infrastructure contracts in Core. Communicate through explicit public operations and avoid circular dependencies or writes to another module's tables.
- Reuse Core's existing `BaseController`, `BaseRequest`, model query traits, and value helpers across resources. Keep leaf classes declarative and place each shared behavior once. Do not insert a repository layer into the Hrm-style controller/model flow or create a separate `Base/` directory or empty placeholders.
- Follow the required placement rules in [ARCHITECTURE.md](./ARCHITECTURE.md#required-placement-rules). Architecture determines code placement; do not add folders first and rewrite the documents afterward to justify them. Ordinary CRUD uses only the defined Controller/Model/Request/View/Route paths, with required schema and authorization wiring. Core's SaaS infrastructure is not a directory template for each resource or module.
- Shared utility classes stay in `app/Helpers/`; existing global functions stay in `app/Helpers/helper.php`. Gateway adapters and their result DTOs stay in `app/Gateways/`. Keep Contracts limited to the existing real module/gateway boundaries, Policies to Laravel authorization, and TenantFinder/Tasks to their Spatie integrations. Do not add ValueObjects/DTOs/Data/Repositories/Actions/Support layers under the current scope; another architectural folder/layer requires an explicit change to the agreed structure before implementation.
- Do not scaffold an API, API route files/resources, token authentication, a separate frontend, or root/module `tests/` directories. These project choices take precedence over generic examples in reusable skills.

## Implementation Standards

- Inspect existing files and conventions before changing code; preserve unrelated user changes. Do not claim planned packages or commands already exist.
- Keep application code easy to read: descriptive names, small focused methods, explicit inputs/results, and visible control/data flow. Avoid clever one-liners, application-level reflection/name guessing, hidden generic dispatch, and layers that only forward calls. Use concise comments to explain non-obvious reasons.
- Follow the Hrm-style flow adapted to Blade: resource controller → `BaseController` → model, and resource request → `BaseRequest`. Leaves declare model/resource metadata; typed `index()` and `store()` delegate to shared `listData()` and `saveData()`. The base owns create/edit/destroy, form preparation, and redirects. Core's concrete `AccountController` serves both `/core/admins` and `/users` through the trusted authentication provider; do not add AdminController/UserController wrappers. `BaseRequest` owns shared authorization, update/target resolution, and uniqueness support; resource requests declare `$rules` or override `rules()` for real differences. `ListRequest` uses the model's query rules. Services receive explicit actors/values/models for actual business operations and return results, not HTTP responses.
- Register module routes through their existing module provider's native `loadRoutesFrom(module_path(...))`; root `routes/web.php` owns home and the shared login/logout/password-recovery routes under `auth`. Each module route file groups `web`/`auth`, its dotted name prefix, and applicable central/tenant restrictions. Declare Core's `prefix('core')` once on that group; its resources live under `/core`, while TenantCore retains `/users`. Use `Route::resource()`, declare the controller once, and use `except()` for unsupported actions. Core's ResourceRegistrar preserves Laravel's resource names/verbs and maps update to `store()`. `BaseController::routePrefix()` derives the prefix from the trusted matched route name (`core.accounts.edit` → `core.accounts`); do not repeat leaf prefix properties, manual route-file includes, or update wrappers. No additional RouteServiceProvider is needed.
- Apply rate limits through route middleware aliases. Prefer Laravel's existing `throttle` alias with a named limiter registered once by the owning provider; do not put rate-limiting logic in Form Requests or controllers. Add custom middleware only for behavior the native middleware cannot express.
- Follow the requested five-part CRUD pattern: Controller, Model, Request, View, and Route. Use a thin `BaseController` leaf, model with the shared query contract, one `BaseRequest` write request, native resource routes, and Blade views containing the index plus one shared create/edit form. Required migrations/policy registration remain schema/security wiring. The base locks/reloads updates, authorizes, fills validated payloads, and saves transactionally. Controllers prepare form values through the protected `formData(Account, Model)` hook. Do not add a service for ordinary CRUD. Services are reserved for substantial provisioning, access, subscription, invoicing, and settlement workflows; no forwarding repositories or copied query bodies.
- Keep models focused on fields, casts, relations, query/display metadata, and intrinsic record facts. Aim for roughly 40 lines per resource model where practical; remove unused or duplicate responsibilities rather than compressing lines or hiding code in new traits/services. Controllers prepare page/form data.
- HTTP field validation and normalization belong only to Requests. Services consume validated payloads; CLI commands use native prompt validation. Do not repeat `Validator` calls or field-format rules in models/services. Retain transactional state/accounting invariants, authorization, and authoritative gateway verification. Applicable text fields require at least 5 characters; passwords share `auth.password_min_length`, currently 5.
- Plan, Role, and Setting use ordinary CRUD without resource services. `PlanRequest` keeps the default slug fixed and its price zero and active flag enabled. Plan/Role policies refuse protected or referenced deletions; shared `BaseController` persistence rechecks authorization after locking a fresh target. Role's existing access transaction locks the owner role and refreshes the actor before target locking; its model retains permission-cache invalidation after commit. `AccountService` calls `SubscriptionService::createUser()` for serialized account quotas; hold the central quota lock until tenant account creation finishes, without retrying a cross-database callback that may already have committed.
- Models own searchable/filterable/sortable fields, allowed includes, eager-load declarations, and safe `$exposed`/relation/count fields through `queryContract()`. Empty exposure fails; list selection defaults to exposure. Write rules and display fields are independent. Never publish `request()->all()` or unrestricted model serialization to a view. Keep intrinsic facts such as tenant statuses and the reserved owner role on their models.
- Use one resource `form.blade.php` for both create and edit, with distinct authorized GET actions. Controllers prepare values, form action, and method; keep queries and business rules outside Blade.
- Settings loads one selected, visible group per request. Use fixed tab buttons and the selected group's direct form; do not loop through all settings groups in the controller or tab view. Save and validation redirects retain that group.
- Handle create and update writes in the controller's single `store()` method. Native resource POST `*.store` and PUT/PATCH `*.update` routes dispatch to it through the shared registrar, with separate authorization and validation. Register explicit model bindings once in the owning provider when the shared method has no model parameter; provider registration also works with cached routes. Resolve the operation from the matched route and scoped bound record, never a body `id`/mode. A missing or invisible update target must fail instead of creating a record.
- Use Blade views, native validation errors/allowed old input, redirects after writes, CSRF protection, method spoofing, and escaped output. Never flash secrets. Prepare query/display data outside Blade.
- Write form fields directly as readable HTML/Blade: labels, inputs, selects, checkboxes, errors, `@csrf`, and `@method`. Use the same Core Bootstrap layout and native Blade partials for genuinely repeated headings/actions/feedback/tables. Do not replace field HTML with helper builders or field components.
- Keep application styling in the single `resources/css/app.css` file, with colors defined once as CSS custom properties and reused through `var()`. Do not add per-page stylesheets or inline styles. Use jQuery through the single `resources/js/app.js` entry point for interactive behavior.
- Use the shared admin shell: dark sidebar with desktop collapse/mobile offcanvas, white topbar and account menu, and consistent compact cards/tables/forms. Core's `LayoutComposer`, registered only for `core::layouts.app`, supplies named menu visibility/URL/active values and scalar site/account/workspace data in `$layout`; use fixed menu HTML with Blade conditionals, keep models and authorization outside Blade, and use no menu loops in either the composer or layout. Dashboard counts/recent records must be actual authorized data prepared outside Blade; do not add invented analytics or inactive controls to fill the design.
- Keep global helper functions limited to reusable logic in `Modules/Core/app/Helpers/helper.php`: `getValue`, `getSelected`, `getChecked`, `inputClass`, `inputAttrs`, and `normalizeEmail`. `getValue` prefers allowed old input over model/default values; selection helpers return `selected`/`checked` attributes. Use `{{ inputAttrs('name') }}` for conditional validation ARIA attributes; optional input/help IDs preserve accessible descriptions. It returns Laravel's escaped attribute bag. Escape values with Blade and leave passwords blank. Helpers must not generate HTML elements or views. Register the file once through Core's module metadata.
- Use `spatie/laravel-permission` with a consistent `web` guard and Laravel policies/gates. Authorize every read/write/workflow action server-side and scope list/lookup/export queries to visible records.
- Password recovery uses native Laravel brokers through `PasswordController`/`PasswordRequest`: `admins` stores central reset tokens and `users` stores tenant tokens. Resolve the host first, use the scoped broker, rate-limit submissions, and never flash passwords/tokens. The default log mailer does not deliver email; configure SMTP or another real mail transport for reset links.
- Keep Role CRUD limited to role names. The separate `/core/permissions` workflow reuses `BaseController`/`BaseRequest`, with service-prepared matrix data and a redirect retaining the selected role. Its full grant update requires `permissions_present=1` and the complete permissions array; `partialUpdates=false` preserves required/present validation, including an intentional empty array. Permission viewing/managing and account role assignment use distinct `permissions.view`, `permissions.manage`, and `roles.assign` abilities. Scope choices to the current database and actor's capabilities, protect the reserved owner role, and serialize access changes through the shared access lock. Group labels come from `config/permissions.php`, never invented authority.
- Use explicit mass-assignment rules and parameterized queries; assign ownership and calculated values through trusted logic. Never expose secrets or silently hide failures.
- Protect database invariants with foreign keys, uniqueness, indexes, transactions, and appropriate concurrency controls. Use exact monetary values, eager-load relationships used by pages, and paginate unbounded lists.
- Scope queries to visible records before applying grouped, allowlisted search/filter/sort. Filter, order, count, and paginate in the database; never load an unbounded collection to filter/page in PHP. Select needed columns plus hydration/relationship keys, eager-load displayed relations, and keep list query counts from growing per row.
- Use native numbered pagination with deterministic ordering and a unique tie-breaker. Default to 10 rows; allowed sizes are 5/10/15/20/30/50/100 and literal `all` (shown as All), which displays every filtered, authorized record on page 1. Size changes reset page 1; preserve validated filters, sorting, and size in links. Justify indexes with common predicates and query plans, including deep-page/count costs. Cache only with a clear invalidation owner; use bounded chunks, `lazyById()`, or jobs for real bulk work. Measure query counts/timings at representative volumes; no pattern guarantees every growing dataset is fast.
- Keep service providers lean: register required bindings/routes/views without database queries, network work, or custom filesystem scans during boot. Keep one root asset pipeline and add providers or abstractions only for real behavior; measure performance before claiming an improvement.
- Use `spatie/laravel-multitenancy` for database switching, execution context and tenant-aware jobs. Resolve domains in web middleware after provider boot; unknown/inactive tenant domains return 404. Keep the request context until response termination for error rendering, streaming and response collectors. Providers never query the registry or run migrations.
- Keep shared account/permission migrations in Core's `database/migrations/shared`, central registry migrations in Core's `database/migrations/central`, and tenant-only migrations in TenantCore's `database/migrations`. A new table/column is a NEW migration; never edit an already-applied migration. `php artisan tenants:migrate` applies pending tenant migrations to every registered tenant, including suspended tenants; `--tenant=ID_OR_SLUG` targets selected tenants, `--pretend` previews, and production requires `--force`. Each database retains its own migration history. Failures continue to other tenants and produce a nonzero exit plus failed IDs; fix and rerun. New tenants use the same paths. Never run `migrate:fresh` across real tenants or migrate during requests/boot.
- Explicit setup checks database ownership and serializes schema work with a MySQL advisory lock. Never replace a foreign ownership marker or drop a tenant database. `tenant:adopt` preserves the existing account/password; `tenant:retry SLUG` resumes unfinished setup, with `--adopt` for explicit adoption. Platform and tenant administrators are separate accounts.
- Tenant forms generate a unique slug from the workspace name and suggest `{slug}.{TENANT_BASE_DOMAIN}`; `platform.localhost` defaults the base to `localhost`. Domains remain editable, and edits preserve existing identifiers unless explicitly changed. Optional address/phone, a strict PNG/JPG/WebP/GIF logo up to 2 MB, and `has_branches` belong to the tenant profile; the flag does not create branch records. Store generated logo paths on the central public disk, preserve old logos on failure, and clean replaced/unreferenced uploads.
- Authorize the HTTP action before `Tenant::execute()`. Inside it, use explicit installation values and the active tenant's models; do not reuse the HTTP actor's gates or another tenant's loaded models. Tenant-aware jobs must check lifecycle eligibility; central jobs explicitly implement Spatie `NotTenantAware` because the package defaults to tenant-aware queues. Database session/queue transport connections stay central.
- Verify browser flows, validation, denied access, applicable business rules, module wiring, and important database invariants through focused manual checks. Do not add automated test scaffolding under the current scope.
- Keep documentation concise and update architecture guidance when an architectural decision changes.

- Settings are fixed grouped records on the active central/tenant connection. `config/settings.php` owns group/field metadata, `SettingRequest` validates input, and the controller prepares direct forms in Bootstrap group tabs; legacy edit URLs redirect to the selected tab, with no edit-icon workflow. Provider credentials and checkout snapshots are encrypted and hidden. Initialize missing settings only during explicit setup/migrations. Tenant settings expose company/branding/general; billing and SSLCommerz/bKash/Nagad/EPS credentials belong centrally. Providers start disabled and require operator credentials/configuration. The layout reads current-plane branding during view composition, never provider boot.
- Plans, subscriptions, invoices, payments, and checkout attempts belong centrally. Store exact integer minor units; subscriptions snapshot their price/currency/interval. A tenant receives the free default Starter plan during setup; deployment enrolls existing eligible tenants without charging them. Allow immediate free-plan changes, preserve the paid current period, and issue paid renewal invoices without automatic charges. Keep financial and lifecycle transitions in their substantial workflows; do not accept calculated totals, settlement status, or billing dates from arbitrary form input.
- Invoice forms offer Draft or Issued; saving Issued requires issue authorization and finalizes the invoice. Paid/partially paid states come from recorded payments. Show `Invoice #ID` when no number exists; issuing a legacy unissued invoice must preserve recorded money and derive its payment status.
- A tenant's manual payment submission stays pending until an authorized platform operator approves or rejects it. Gateway settlement requires authoritative provider verification matching the stored checkout order, amount, and currency; browser redirects or supplied references are not proof. Reject sandbox settlement in production. Configure a public HTTPS canonical central callback base through `PAYMENT_CALLBACK_BASE_URL`; live-provider claims require merchant-specific verification.

## Commands

Use the application's Composer/npm manifests and [README.md](./README.md): `php artisan serve` serves the starter with built assets; `composer dev` starts Laravel and Vite together; `composer lint`, `composer format`, and `npm run build` provide the configured checks/formatting/build. Use `composer optimize` for production config/event/route/view caches after environment setup. `composer optimize-clear` clears generated caches while preserving application-cache entries; keep ordinary development uncached. Run checks relevant to the change; report unavailable checks and why. Do not invent build/generation commands or claim verification of unimplemented features.

`platform:migrate` updates central schema, settings, permissions, and the free default plan; `tenants:migrate` updates shared/tenant schema and tenant settings. Laravel schedules `GenerateDueInvoices` hourly; the Invoices button dispatches the same workflow, and `subscriptions:sync --force` remains a manual command. `payments:reconcile --force` runs every five minutes. Production must run `schedule:run` every minute; these operations do not authorize automatic customer charges.
