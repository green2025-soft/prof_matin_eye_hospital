# Project Guidelines

These instructions apply to this workspace. [ARCHITECTURE.md](./ARCHITECTURE.md) defines the application structure and coding conventions.

## Current Application and AI Tools

- This is a reusable Laravel 13 modular boilerplate at the project root on PHP `^8.4.1`, with Blade, Bootstrap 5, Popper, jQuery, Font Awesome Free 7.3.1, and Vite. Use Bootstrap; do not add Tailwind. Font Awesome core/solid styles are bundled locally through Vite.
- `nwidart/laravel-modules` 13.0.0, its Composer merge integration, `spatie/laravel-permission` 8.3.2, and `spatie/laravel-multitenancy` 4.2.2 are installed. Exactly two modules exist: Core owns platform/shared infrastructure and the tenant/domain registry; TenantCore owns `Modules\TenantCore\Models\User` and tenant account operations through Core's `TenantAccounts` contract.
- Native Spatie tenant switching selects a separate database per tenant. Core's Admin uses the central database; TenantCore's User uses the selected tenant connection. Both inherit shared Account behavior and use the public `web` guard. Login/logout, host/session/remember-cookie isolation, explicit provisioning/adoption, all-tenant migrations, tenant management, account management, and role/permission forms are implemented. Project-specific business workflows remain unspecified.
- Preserve the existing `.env`, application key, credentials, and database data. File sessions/cache and a synchronous queue remain the development defaults. The health route needs no database; tenant domain resolution requires the installed central registry. Database creation and migration run only through explicit installation/provisioning/deployment commands.
- Apply the bundled [Laravel fullstack skill](./.agents/skills/laravel-fullstack-development/SKILL.md) and [Laravel best practices](./.agents/skills/laravel-best-practices/SKILL.md) when relevant. Project instructions override their generic Vue/API/JWT, tenancy, and hierarchy examples.
- Keep `.agents/skills/` and [.codex/config.toml](./.codex/config.toml) with the project for portable native skill discovery and Laravel Boost MCP. Do not depend on a username, drive, or global plugin cache. The receiving PC still needs Codex and the application's runtime dependencies.
- Boost-generated guidelines are disabled; testing and Tailwind skills are excluded through [boost.json](./boost.json) and [config/boost.php](./config/boost.php). Preserve these decisions when updating Boost.

## Architecture

- Build one modular Laravel web application with Blade, HTML forms, Bootstrap, and session authentication on the `web` guard.
- Keep exactly two modules at the project root: `Modules/Core` and `Modules/TenantCore`, alongside Laravel's `app/` directory. This boilerplate foundation comes before project-specific work.
- Create an explicitly approved module with native `php artisan module:make ModuleName`, supplying the required name; inspect modules with `php artisan module:list`. Do not hand-scaffold modules or regenerate/force-overwrite the existing Core and TenantCore. Adding another module requires an explicit change to the current two-module scope.
- Use the standard `nwidart/laravel-modules` layout: module PHP code in `Modules/{Module}/app/` with `Modules\{Module}\...` namespaces; module routes, views, migrations, and seeders in lowercase `routes/`, `resources/views/`, and `database/` paths. Keep each module's `composer.json`, `module.json`, providers, and registration consistent.
- Keep the configured generator lean: module/Composer metadata, a functional provider, and lowercase `routes/web.php` with one `web` middleware/module URL prefix/route-name prefix group; register views/schema when added and reuse the Core layout. Module creation supplies a skeleton, not an authorized CRUD feature. Do not generate fake controllers, views, models, resources, frontend builds, APIs, tests, or factories; actual CRUD work follows the recipe below.
- Core owns platform/shared infrastructure and must not depend on concrete TenantCore classes. TenantCore owns the tenant-facing foundation and the authoritative User model. Integrate through owner-defined contracts when a real boundary requires them.
- Laravel authentication selects Core's Admin for trusted central hosts and TenantCore's User for active registered tenant domains. Keep both on guard `web`; retain Laravel's native SessionGuard with context-specific session and remember-cookie names. Do not duplicate either identity model.
- Keep project-specific business structure unspecified until requirements are available. Do not invent business feature modules or additional model hierarchies.
- Keep contracts with their owner; place genuine shared infrastructure contracts in Core. Communicate through explicit public operations and avoid circular dependencies or writes to another module's tables.
- Reuse Core's existing `BaseController`, `BaseRequest`, model query traits, and value helpers across resources. Keep leaf classes declarative and place each shared behavior once. Do not insert a repository layer into the Hrm-style controller/model flow or create a separate `Base/` directory or empty placeholders.
- Do not scaffold an API, API route files/resources, token authentication, a separate frontend, or root/module `tests/` directories. These project choices take precedence over generic examples in reusable skills.

## Implementation Standards

- Inspect existing files and conventions before changing code; preserve unrelated user changes. Do not claim planned packages or commands already exist.
- Keep application code easy to read: descriptive names, small focused methods, explicit inputs/results, and visible control/data flow. Avoid clever one-liners, application-level reflection/name guessing, hidden generic dispatch, and layers that only forward calls. Use concise comments to explain non-obvious reasons.
- Follow the Hrm-style flow adapted to Blade: resource controller → `BaseController` → model, and resource request → `BaseRequest`. Leaves declare `$model`, `$title`, `$service`, `$views`, `$parameter`, and `$routePrefix`. A typed `store(ResourceRequest $request)` delegates to `saveData()` for Laravel's native validation; do not copy inherited index/create/edit/destroy bodies. `BaseRequest` owns shared authorization, update/target resolution, and uniqueness support; resource requests declare `$rules` or override `rules()` for real differences. `ListRequest` uses the model's query rules. Services receive explicit actors/values/models for actual business operations and return results, not HTTP responses.
- Use `Route::resource()` for every CRUD and group shared middleware/name prefixes. Keep protected module resources under one common authenticated group; home/login/logout retain their explicit route contracts. Add central/tenant restrictions within that group. Declare the controller once and use `except()` for unsupported actions. Core's ResourceRegistrar preserves Laravel's resource names/verbs and maps update to inherited `store()` once. Do not repeat manual CRUD routes or update wrappers. End name prefixes with a dot and retain per-action authorization.
- Apply rate limits through route middleware aliases. Prefer Laravel's existing `throttle` alias with a named limiter registered once by the owning provider; do not put rate-limiting logic in Form Requests or controllers. Add custom middleware only for behavior the native middleware cannot express.
- Follow one CRUD recipe: model with `HasCrudContract`/`HandlesModelQueries`, one write Form Request extending `BaseRequest`, thin controller extending `BaseController`, `index.blade.php`, one `form.blade.php`, the owning migration, and named resource routes/policies. Shared model query methods provide search/filter/eager-load/pagination execution directly; do not add repositories or copy query bodies into controllers. Add a show view or write service only for a real consumer or business rule.
- Models own searchable/filterable/sortable fields, allowed includes, eager-load declarations, and safe `$exposed`/relation/count fields through `queryContract()`. Empty exposure fails; list selection defaults to exposure. Write rules and display fields are independent. Never publish `request()->all()` or unrestricted model serialization to a view. Keep intrinsic facts such as tenant statuses and the reserved owner role on their models.
- Use one resource `form.blade.php` for both create and edit, with distinct authorized GET actions. Controllers prepare values, form action, and method; keep queries and business rules outside Blade.
- Handle create and update writes in the controller's single `store()` method. Native resource POST `*.store` and PUT/PATCH `*.update` routes dispatch to it through the shared registrar, with separate authorization and validation. Register explicit model bindings once in the owning provider when the shared method has no model parameter; provider registration also works with cached routes. Resolve the operation from the matched route and scoped bound record, never a body `id`/mode. A missing or invisible update target must fail instead of creating a record.
- Use Blade views, native validation errors/allowed old input, redirects after writes, CSRF protection, method spoofing, and escaped output. Never flash secrets. Prepare query/display data outside Blade.
- Write form fields directly as readable HTML/Blade: labels, inputs, selects, checkboxes, errors, `@csrf`, and `@method`. Use the same Core Bootstrap layout and native Blade partials for genuinely repeated headings/actions/feedback/tables. Do not replace field HTML with helper builders or field components.
- Keep application styling in the single `resources/css/app.css` file, with colors defined once as CSS custom properties and reused through `var()`. Do not add per-page stylesheets or inline styles. Use jQuery through the single `resources/js/app.js` entry point for interactive behavior.
- Use the shared admin shell: dark sidebar with desktop collapse/mobile offcanvas, white topbar and account menu, and consistent compact cards/tables/forms. Dashboard counts/recent records must be actual authorized data prepared outside Blade; do not add invented analytics or inactive controls to fill the design.
- Keep helpers limited to reusable logic in `Modules/Core/app/Helpers/helper.php`: `getValue`, `getSelected`, `getChecked`, `inputClass`, `inputAttrs`, and `normalizeEmail`. `getValue` prefers allowed old input over model/default values; selection helpers return `selected`/`checked` attributes. Use `{{ inputAttrs('name') }}` for conditional validation ARIA attributes; optional input/help IDs preserve accessible descriptions. It returns Laravel's escaped attribute bag. Escape values with Blade and leave passwords blank. Helpers must not generate HTML elements or views. Register the file once through Core's module metadata.
- Use `spatie/laravel-permission` with a consistent `web` guard and Laravel policies/gates. Authorize every read/write/workflow action server-side and scope list/lookup/export queries to visible records.
- Keep Role CRUD limited to role names. Permission grants belong to the separate `/permissions` role-selection workflow with distinct `permissions.view` and `permissions.manage` abilities; account role assignment uses `roles.assign`. Scope available roles and permissions to the actor's current database and capabilities. Preserve existing grants when saving a role name, protect the reserved owner role, and serialize access changes through the shared access lock. Group display labels come from `config/permissions.php`; permissions are never invented from display metadata.
- Use explicit mass-assignment rules and parameterized queries; assign ownership and calculated values through trusted logic. Never expose secrets or silently hide failures.
- Protect database invariants with foreign keys, uniqueness, indexes, transactions, and appropriate concurrency controls. Use exact monetary values, eager-load relationships used by pages, and paginate unbounded lists.
- Scope queries to visible records before applying grouped, allowlisted search/filter/sort. Filter, order, count, and paginate in the database; never load an unbounded collection to filter/page in PHP. Select needed columns plus hydration/relationship keys, eager-load displayed relations, and keep list query counts from growing per row.
- Use native numbered pagination with deterministic ordering and a unique tie-breaker. Default to 10 rows and allow only 5, 10, 15, 20, 30, 50, or 100; preserve validated filters, sorting, and page size in pagination links. Justify indexes with common predicates and query plans, including deep-page/count costs. Cache only with a clear invalidation owner; use bounded chunks, `lazyById()`, or jobs when a real bulk workload requires them. Measure query counts/timings at representative data volumes; no pattern guarantees every growing dataset is fast.
- Keep service providers lean: register required bindings/routes/views without database queries, network work, or custom filesystem scans during boot. Keep one root asset pipeline and add providers or abstractions only for real behavior; measure performance before claiming an improvement.
- Use `spatie/laravel-multitenancy` for database switching, execution context and tenant-aware jobs. Resolve domains in web middleware after provider boot; unknown/inactive tenant domains return 404. Keep the request context until response termination for error rendering, streaming and response collectors. Providers never query the registry or run migrations.
- Keep shared account/permission migrations in Core's `database/migrations/shared`, central registry migrations in Core's `database/migrations/central`, and tenant-only migrations in TenantCore's `database/migrations`. A new table/column is a NEW migration; never edit an already-applied migration. `php artisan tenants:migrate` applies pending tenant migrations to every registered tenant, including suspended tenants; `--tenant=ID_OR_SLUG` targets selected tenants, `--pretend` previews, and production requires `--force`. Each database retains its own migration history. Failures continue to other tenants and produce a nonzero exit plus failed IDs; fix and rerun. New tenants use the same paths. Never run `migrate:fresh` across real tenants or migrate during requests/boot.
- Explicit setup checks database ownership and serializes schema work with a MySQL advisory lock. Never replace a foreign ownership marker or drop a tenant database. `tenant:adopt` preserves the existing account/password; `tenant:retry SLUG` resumes unfinished setup, with `--adopt` for explicit adoption. Platform and tenant administrators are separate accounts.
- Authorize the HTTP action before `Tenant::execute()`. Inside it, use explicit installation values and the active tenant's models; do not reuse the HTTP actor's gates or another tenant's loaded models. Tenant-aware jobs must check lifecycle eligibility; central jobs explicitly implement Spatie `NotTenantAware` because the package defaults to tenant-aware queues. Database session/queue transport connections stay central.
- Verify browser flows, validation, denied access, applicable business rules, module wiring, and important database invariants through focused manual checks. Do not add automated test scaffolding under the current scope.
- Keep documentation concise and update architecture guidance when an architectural decision changes.

## Commands

Use the application's Composer/npm manifests and [README.md](./README.md): `php artisan serve` serves the starter with built assets; `composer dev` starts Laravel and Vite together; `composer lint`, `composer format`, and `npm run build` provide the configured checks/formatting/build. Use `composer optimize` for production config/event/route/view caches after environment setup. `composer optimize-clear` clears generated caches while preserving application-cache entries; keep ordinary development uncached. Run checks relevant to the change; report unavailable checks and why. Do not invent build/generation commands or claim verification of unimplemented features.
