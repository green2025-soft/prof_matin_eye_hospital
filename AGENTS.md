# Project Guidelines

These instructions apply to this workspace. [ARCHITECTURE.md](./ARCHITECTURE.md) defines the application structure and coding conventions.

## Current Application and AI Tools

- This is a reusable Laravel 13 modular boilerplate at the project root on PHP `^8.4.1`, with Blade, Bootstrap 5, Popper, jQuery, Font Awesome Free 7.3.1, and Vite. Use Bootstrap; do not add Tailwind. Font Awesome core/solid styles are bundled locally through Vite.
- `nwidart/laravel-modules` 13.0.0, its Composer merge integration, `spatie/laravel-permission` 8.3.2, and `spatie/laravel-multitenancy` 4.2.2 are installed. Approved modules are Core, TenantCore, Hospital, Pharmacy, and Prescription. Pharmacy owns the approved Medicine/Optic catalog, purchase/sales/returns, branch stock movements and transfers, payments, reports, and new-tenant catalog seeding. Core owns platform/shared infrastructure and the tenant/domain registry; TenantCore owns `Modules\TenantCore\Models\User`, tenant account operations through Core's `TenantAccounts` contract, Branch, Payment Type, and Division/District/Thana CRUD, read-only Audit Logs, and the shared module dashboard. Hospital owns its separate menu and approved Investigation Category, Investigation, Operation Category, Operation, Patient, Doctor Department, Doctor, Appointment, Consultation, Patient Investigation, Patient Operation, Refund Cause, Refund, and Due Collection resources; further hospital features await requirements.
- Native Spatie tenant switching selects a separate database per tenant. Core Admin uses the central database; TenantCore User and Hospital Doctor use the selected tenant connection and shared Account behavior on the public `web` guard. Doctor profile and credentials live only in `doctors`, without a row or link in `users`. The foundation includes login/logout/password recovery, context isolation, explicit setup/adoption/migrations, tenant/account/access management, plans/subscriptions, invoices/payments, checkout, and grouped settings. Further business workflows require requirements; live gateway verification requires operator credentials and reachable callbacks.
- Preserve the existing `.env`, application key, credentials, and database data. File sessions/cache and a synchronous queue remain the development defaults. The health route needs no database; tenant domain resolution requires the installed central registry. Database creation and migration run only through explicit installation/provisioning/deployment commands.
- Apply the bundled [Laravel fullstack skill](./.agents/skills/laravel-fullstack-development/SKILL.md) and [Laravel best practices](./.agents/skills/laravel-best-practices/SKILL.md) when relevant. Project instructions override their generic Vue/API/JWT, tenancy, and hierarchy examples.
- Keep `.agents/skills/` and [.codex/config.toml](./.codex/config.toml) with the project for portable native skill discovery and Laravel Boost MCP. Do not depend on a username, drive, or global plugin cache. The receiving PC still needs Codex and the application's runtime dependencies.
- Boost-generated guidelines are disabled; testing and Tailwind skills are excluded through [boost.json](./boost.json) and [config/boost.php](./config/boost.php). Preserve these decisions when updating Boost.

## Architecture

- Build one modular Laravel web application with Blade, HTML forms, Bootstrap, and session authentication on the `web` guard.
- Keep approved modules at the project root alongside Laravel's `app/`: Core, TenantCore, Hospital, Pharmacy, and Prescription. Further modules require an explicitly approved name; do not invent business features.
- Create an explicitly approved module with native `php artisan module:make ModuleName`, supplying the required name; inspect modules with `php artisan module:list`. Do not hand-scaffold modules or regenerate/force-overwrite existing modules. Hospital is explicitly approved; future modules still require approval of their names and scope.
- Use the standard `nwidart/laravel-modules` layout: module PHP code in `Modules/{Module}/app/` with `Modules\{Module}\...` namespaces; module routes, views, migrations, and seeders in lowercase `routes/`, `resources/views/`, and `database/` paths. Keep each module's `composer.json`, `module.json`, providers, and registration consistent.
- Keep the configured generator lean: module/Composer metadata, a functional provider using native `loadRoutesFrom()`, and lowercase `routes/web.php` with one `web`/`auth` middleware/module URL prefix/route-name prefix group; register views/schema when added and reuse the Core layout. Module creation supplies a skeleton, not an authorized CRUD feature. Do not generate fake controllers, views, models, resources, frontend builds, APIs, tests, or factories; actual CRUD work follows the recipe below.
- TenantCore owns `ModuleDashboardController` and shared module chooser/landing views. Tenant root defaults to `/module-dashboard`, custom user redirects remain respected, `/workspace` retains the tenant overview, and platform root is unchanged. Use native `Module::getOrdered('desc')` with enabled modules' `tenant_dashboard` metadata; Core has no tenant card. Protected cards require role permission and usable-plan access, with independent route authorization. Hospital resource pages and `/hospital` landing use `auth`/`tenant`/`subscribed`/`branch:required` plus `hospital.view`, also present in Plan Permissions; read-only catalog selectors use separate authenticated-tenant-only routes. New approved modules declare metadata and their own authorized named route; do not create a custom scanner/catalog layer. Investigation Category, Investigation, Operation Category, Operation, Patient, Doctor Department, Doctor, Appointment, Consultation, Patient Investigation, and Patient Operation are approved Hospital resources; Hospital also owns a dedicated permission-scoped dashboard with today's branch activity, recent appointments/patients and authorized quick entry. Further business features await requirements. Declare Hospital migrations explicitly in tenant migration paths, never through boot scans.
- Core owns platform/shared infrastructure and must not depend on concrete TenantCore classes. TenantCore owns the tenant-facing foundation and the authoritative User model. Integrate through owner-defined contracts when a real boundary requires them.
- Hospital owns `MenuComposer`, registered only for `core::layouts.app`, and its fixed menu partial with native `<details>` Transactions, People, and Setup groups. On `hospital.*` requests it reads the middleware-prepared `navigation_permissions` request attribute into the scalar `$moduleMenu['permissions']` map; it has no per-resource blocks or permission-computation fallback. Grouped permission middleware validates actor context, uses the current-plane catalog for owners or actual grants for other actors, and applies usable-plan limits while retaining Billing recovery access. Fixed menu HTML checks that map and uses native `route()`/`request()->routeIs()` for URL/active presentation, without models, gates, queries, or menu loops in Blade. Core retains common Dashboard/Modules links and must not import Hospital models or contain Hospital business permission guards. Future ordinary CRUD needs no composer changes.
- Laravel authentication defaults to Core Admin centrally and TenantCore User on tenant hosts. Core's `Services/CachedUserProvider.php` extends Laravel's `EloquentUserProvider` only to cache GET/HEAD session-ID restoration; credential, remember-token, and customized provider lookups keep native database reads. Enabled Hospital registers its own `Services/HospitalUserProvider.php` adapter, Doctor provider/password broker, and login-type metadata through its existing provider. Core consumes generic registered login types with User as the default; it contains no Doctor imports or Doctor-table queries, and User login/recovery stays native when Hospital is absent or disabled. Keep Laravel's unchanged public `web` SessionGuard and scoped session/remember-cookie names. Explicit type selection delegates to configured Eloquent models, with numeric User IDs or `doctor:<id>` in native guard session/remember values; never guess by email. Doctor data stays wholly in `doctors`.
- Keep project-specific business structure unspecified until requirements are available. Do not invent business feature modules or additional model hierarchies.
- Keep contracts with their owner; place genuine shared infrastructure contracts in Core. Communicate through explicit public operations and avoid circular dependencies or writes to another module's tables.
- Reuse Core's existing `BaseController`, `BaseRequest`, model query traits, and value helpers across resources. Core's Eloquent `Models\BaseModel` owns `HasCrudContract` and the shared opt-in branch scope/ownership checks; central `CoreModel` and the TenantCore/Hospital/Pharmacy module `BaseModel` classes extend it, with `UsesTenantConnection` owned by each tenant module base. Setting uses the neutral Core base on the active database; Account and Spatie Role keep their native parents. Keep leaf classes declarative and place each shared behavior once. Do not insert a repository layer into the Hrm-style controller/model flow or create a separate `Base/` directory or empty placeholders.
- Follow the required placement rules in [ARCHITECTURE.md](./ARCHITECTURE.md#required-placement-rules). Architecture determines code placement; do not add folders first and rewrite the documents afterward to justify them. Ordinary CRUD uses only the defined Controller/Model/Request/View/Route paths, with required schema and authorization wiring. Core's SaaS infrastructure is not a directory template for each resource or module.
- Shared utility classes stay in `app/Helpers/`; existing global functions stay in `Modules/Core/app/Helpers/helper.php`. Gateway adapters and their result DTOs stay in `app/Gateways/`. Keep Contracts limited to the existing real module/gateway boundaries, Policies to Laravel authorization, and TenantFinder/Tasks to their Spatie integrations. Do not add ValueObjects/DTOs/Data/Repositories/Actions/Support layers under the current scope; another architectural folder/layer requires an explicit change to the agreed structure before implementation.
- Do not scaffold an API, API route files/resources, token authentication, a separate frontend, or root/module `tests/` directories. These project choices take precedence over generic examples in reusable skills.

## Implementation Standards

- Prescription is an approved separate module and contains independent General Prescription and Glass Prescription resources. Both follow the normal Controller/Model/Request/View/Route flow through Core BaseController/BaseRequest and native resource routes. Only General uses PrescriptionService for its header/medicine aggregate; Glass is ordinary CRUD with no service or shared type dispatcher. The module reads Hospital Patient/Doctor and Pharmacy Medicine through native relations/selectors and never writes their tables. Its tenant tables are prescriptions, prescription_medicines and glass_prescriptions. Module-owned settings at /prescription/settings reuse the neutral Setting model/group and control feature availability, optional sections and A4/A5/header printing. Core's default-true isCrudEnabled() intrinsic hook is enforced by the unchanged generic CRUD authorization pipeline; each owning resource supplies its own availability fact. Prescription caches those settings only within safe read requests and keys them by tenant database; writes always read current settings. Register the explicit tenant migration path and module dashboard metadata, not migration scans or extra per-resource middleware.
- General Prescription uses a compact pad with Bootstrap section modals; modal controls outside the main form explicitly use `form="prescription-form"`. History and examination details use separate whitelisted JSON fields; follow-up notes remain text. The six identical clinical pickers store per-name duration/unit/notes in `section_details`; their shared row editor performs the same work for all six. Follow-up keeps its separate date/phrase flow. Tenant-wide `prescription_options` stores identical section/name/ordering presets, medicine-unit labels and instructions through ordinary inline CRUD. Medicine and Investigation choices reuse their existing catalogs. Patient creation reuses Hospital's existing modal and service. Keep jQuery in dedicated ESM files for page coordination, identical picker operations, clinical item rows, previews, examination controls and Rx editing; never add resource dispatch to a shared picker. The pad uses the provided `public/prescription-bg.png` asset.
- `BaseController::saveData()` keeps native redirects by default. Its explicit optional JSON response flag supports web AJAX catalog creation after the same transactional authorization/persistence; JSON contains only the model's exposed fields. Ordinary callers retain their existing redirect signatures and behavior.
- Format all controllers consistently: each associative array/object entry occupies its own line, and fluent query chains place each method call on a separate line. Keep short scalar column/rule lists compact. In Blade, group short attributes on one line and wrap long attributes/helper calls; do not force every attribute onto its own line or create horizontal scrolling. Use blank lines between input preparation, queries, prepared view data and responses; do not change behavior just to format code.
- Prepare report view values in a local `$data` array, then render with `return view('pharmacy::reports.report-name', $data);`; do not place the data array inline in `view()`.
- Pharmacy reports each own an explicit named route, report controller in `app/Http/Controllers/Reports/` extending Core BaseController, and report Blade view. Do not route report names through a controller switch or dynamic view include. ReportService shares only unchanged stock-product filtering, due aggregation and daily arithmetic; necessary chunk streams retain exact integer totals. DateRangeReportRequest validates common period defaults; ReportComposer prepares the same branch/company letterhead for reports/layout. Print report prints the currently displayed results on the same page; only the user-selected All page size loads all filtered rows. Reports use A4 portrait (Stock/Profit-Loss landscape), repeated table headings and signature/footer metadata without altering transaction data.
- Pharmacy money column names have no `_minor` suffix (`unit_price`, `cost`, `total`, `paid`, and similar fields). Transaction and stock money values remain exact integer minor units; keep the existing Money conversions at form/display boundaries. This naming change does not alter the Product catalog's decimal prices or Core billing columns.
- Pharmacy uses native Eloquent relationships, eager loading, scopes, withSum/withCount, and native aggregates. Do not write raw SQL, raw expressions, or manual joins in Pharmacy application workflows. Each of Purchase, Sale, PurchaseReturn, SaleReturn, Adjustment, OpeningStock, Wastage, and Transfer has exactly its own header/item table pair. No inventory_documents or inventory_document_lines table/view remains. Stock ledgers identify owners with native polymorphic type/ID pairs; returns and the two payment-allocation tables use concrete foreign keys. The explicit 2026-11-03 reset migration discards old Pharmacy transactions, payments, and derived stock history as requested; catalogs, sequences, settings, patients, and other modules remain.
- All 34 Pharmacy tables use the `phr_` prefix. Resource item FKs are native (`purchase_id`, `sale_id`, `purchase_return_id`, `sale_return_id`, `adjustment_id`, `opening_stock_id`, `wastage_id`, `transfer_id`); return originals use `purchase_id`/`purchase_item_id` or `sale_id`/`sale_item_id`. Payment allocations use native purchase/sale IDs and relations. Do not introduce generic document IDs, source-document IDs, or parent-relation aliases. Only shared stock ledgers use native `stock_entry_type/id`, `stock_item_type/id`, and `source_item_type/id` morph ownership. Stock entry dates use `entry_date`.
- Each Pharmacy main/item table stores only fields used by that resource. Never add unused columns to satisfy a shared persistence method. StockEntry/StockItem expose only true common fields; payment, invoice totals, return balances and revision state stay with their financial owners. Opening Stock items have 13 columns: id, opening_stock_id, variant_id, product_unit_id, quantity, factor, base_quantity, unit_price, cost, batch_no, expiry_date, created_at, updated_at. Opening creates its own receipt lots and has no stock_lot_id, returned/refunded balances, Discount, VAT, payment, revision or soft-delete columns. Adjustment items have 15 columns, Wastage 11 and Transfer 10; selected lots belong only to Adjustment/Wastage. product_type identifies Medicine/Optic menu ownership, while transaction kind comes from the resource/table. FIFO/LIFO snapshots belong only to operations that consume stock. Shared financial helpers receive actual invoice models and explicit money values; shared stock helpers receive explicit lot criteria.


- Apply the same sharing rule across the entire project: a shared operation must perform the same work for every caller. Do not put resource-specific `if`/`else`, `switch`, `match`, or ternary dispatch in shared controllers, services, JavaScript, helpers, or Blade partials. Do not force reuse by checking Purchase/Sale, another model/type, or resource-specific field presence to select different behavior. Keep differing rules and fields in their own resource implementation; share only the unchanged operations. Do not hide the same dispatch behind generic configuration maps, guessed names, or forwarding layers. Common validation and state guards remain shared only when their meaning is identical for every caller. This applies to Core, TenantCore, Hospital, Pharmacy, and future approved work.
- Use the locally Vite-bundled jQuery Toastr for CRUD success/error/warning/info notifications through `window.showToast(message, type = 'info')`. Shared feedback converts flash messages and non-field `record` workflow errors to escaped toast messages. Keep field validation inline and in its existing summary; do not replace confirmation prompts or loading feedback with notifications. Toastr uses the existing jQuery version and an `app-toast` class to avoid Bootstrap's toast component styles.
- Inspect existing files and conventions before changing code; preserve unrelated user changes. Do not claim planned packages or commands already exist.
- Keep application code easy to read: descriptive names, small focused methods, explicit inputs/results, and visible control/data flow. When a controller action uses the authenticated account more than once, assign `$actor = $request->user('web')` locally and reuse it; do not add a forwarding helper or constructor-held actor. Avoid clever one-liners, application-level reflection/name guessing, hidden generic dispatch, and layers that only forward calls. Use concise comments to explain non-obvious reasons.
- Follow the Hrm-style flow adapted to Blade: resource controller → `BaseController` → model, and resource request → `BaseRequest`. Leaves declare model/resource metadata; typed `index()` and `store()` delegate to shared `listData()` and `saveData()`. The base owns create/edit/destroy, form preparation, and redirects. Core's concrete `AccountController` serves `/core/admins` and the configured primary User at `/users`, including when the actor is a Doctor; do not add AdminController/UserController wrappers. `BaseRequest` owns shared authorization, update/target resolution, and uniqueness support; resource requests declare `$rules` or override `rules()` for real differences. `ListRequest` uses the model's query rules. Services receive explicit actors/values/models for actual business operations and return results, not HTTP responses.
- Register module routes through their existing module provider's native `loadRoutesFrom(module_path(...))`; root `routes/web.php` owns home and the shared login/logout/password-recovery routes under `auth`. Each module route file groups `web`/`auth`, its dotted name prefix, and applicable central/tenant restrictions. Group shared middleware instead of repeating it on individual routes. Declare Core's `prefix('core')` once on that group; its resources live under `/core`, while TenantCore retains `/users`. Use `Route::resource()` for multiple CRUD actions, with `except()` for unsupported actions; define a single action with an explicit GET/POST route. Core's ResourceRegistrar preserves Laravel's resource names/verbs and maps update to `store()`. `BaseController::routePrefix()` derives the prefix from the trusted matched route name (`core.accounts.edit` → `core.accounts`); do not repeat leaf prefix properties, manual route-file includes, or update wrappers. No additional RouteServiceProvider is needed.
- Apply rate limits through route middleware aliases. Prefer Laravel's existing `throttle` alias with a named limiter registered once by the owning provider; do not put rate-limiting logic in Form Requests or controllers. Add custom middleware only for behavior the native middleware cannot express.
- Group named route authorization through the existing `core.permission`, `tenantcore.permission`, `hospital.permission`, `pharmacy.permission`, and `prescription.permission` aliases backed by Core's `EnsureModulePermission`. Owning providers configure any required module permission once; do not copy the middleware or add per-resource middleware arguments. The middleware builds `navigation_permissions` once per request from actor context, current-plane grants and usable-plan limits, then checks mapped route requirements/alternatives. Controllers, policies, helpers and composers reuse that scalar map without recomputing permission or plan access. Explicit authenticated landing/recovery routes and catalog selectors retain their intended access. Native record policies consume scalar permission facts and retain target/domain/state safeguards; locked write checks retain grant-containment and financial invariants.
- Follow the requested five-part CRUD pattern: Controller, Model, Request, View, and Route. Use a thin `BaseController` leaf, model with the shared query contract, one `BaseRequest` write request, native resource routes, and Blade views containing the index plus one shared create/edit form. Required migrations and shared authorization remain schema/security wiring. Simple resources declare an explicit `$crudPermission` prefix on their model; Core registers common CRUD gates once through `BaseModel::allowsCrud()`. Empty metadata denies generic access. Shared checks consume the middleware permission map and enforce actor context, record connection, branch/feature availability, and existing records for update/delete. Generic deletion also checks the model's intrinsic `hasReferences()` hook, which defaults to false. Dedicated policies retain precedence for business-specific abilities and invariants and are associated through native model `#[UsePolicy]` attributes; they reuse scalar permission facts rather than recomputing route grants. Do not create a separate policy for simple CRUD. The base locks/reloads updates, authorizes, fills validated payloads, and saves transactionally. Opt-in uploads use explicit input/column mappings: native `afterRollBack` cleans new files and `afterCommit` cleans replaced/deleted files. Controllers prepare form values through the protected `formData(Account, Model)` hook. Do not add a service for ordinary CRUD unless explicitly approved; PatientService handles reusable patient creation/ID allocation, DoctorService owns the actual identity/profile, picture, and shared-permission lifecycle, and Hospital's owning clinical services handle their respective aggregates using only identical operations from abstract ClinicalEntryService and ClinicalInvoiceService. Pharmacy resource services, StockService, and PaymentService own their actual aggregate posting, receipt allocation/reversal, and settlement workflows; its ordinary catalog CRUD still has no service. Other services are reserved for substantial audit capture, provisioning, access, subscription, invoicing, and settlement workflows; no forwarding repositories or copied query bodies.
- Completed CRUDs share this flow. TenantCore's Division/District/Thana and Hospital's tenant-wide catalogs use permission metadata/shared gates without resource policies; geography parents, Investigation Category, Operation Category, and Department add intrinsic reference hooks. Branch retains its chooser/fixed-assignment policy. Core account/access, settings, tenant, and financial resources retain their real business policies and substantial services. Model-declared policies include shared Account behavior inherited by Admin/User; Doctor declares its own record-context, self-delete and shared-grant-containment policy; grouped middleware owns its named route permissions. Core, TenantCore, and Hospital providers contain no per-resource policy/binding tables; native binding scopes belong on the owning model, including Role's `web` guard and Invoice's current-tenant filter.
- Keep models focused on fields, casts, relations, query/display metadata, and intrinsic record facts. Aim for roughly 40 lines per resource model where practical; remove unused or duplicate responsibilities rather than compressing lines or hiding code in new traits/services. Controllers prepare page/form data.

Categories and investigations are tenant-wide across all branches with no `branch_id`, despite the Hospital entry's required selection.
