# Laravel Modular Boilerplate

Reusable Laravel 13 foundation with three approved modules: **Core** for platform/shared infrastructure, **TenantCore** for tenant accounts, Branch, Payment Type, and Division/District/Thana CRUD, read-only Audit Logs, and the shared module dashboard, and **Hospital** for its separate menu and approved Investigation Category, Investigation, Operation Category, Operation, Patient, Doctor Department, Doctor, Appointment, Consultation, Patient Investigation, Patient Operation, Refund Cause, Refund, and Due Collection resources. It uses Blade, Bootstrap 5, jQuery, locally bundled Font Awesome Free 7.3.1, and Vite. Spatie multitenancy provides separate tenant databases and native context switching; platform and tenant accounts share session authentication with isolated identities. The foundation includes tenant/account/access management, plans/subscriptions, invoices/payments, checkout, and grouped settings. Approved clinical entry workflows are described below; further business features require requirements.

## Requirements

- PHP 8.4.1 or later within PHP 8, with the extensions required by Composer.
- Composer 2 and Node.js compatible with Vite 8: Node 20.19.x or Node 22.12 and later.
- MySQL when application database connections and module migrations are configured.

## Local setup

From the project root:

```powershell
composer install
npm ci
```

Only for a fresh checkout without an existing `.env`:

```powershell
Copy-Item .env.example .env
php artisan key:generate
```

Preserve an existing `.env` and application key. Configure MySQL credentials, `DB_CONNECTION=central`, `CENTRAL_DB_DATABASE`, and `CENTRAL_DOMAINS` in `.env`. The default platform host is `localhost`: use `APP_URL=http://localhost:8000` and `CENTRAL_DOMAINS=localhost` locally. The central database must differ from any tenant database. Optional `DB_PROVISION_USERNAME`/`DB_PROVISION_PASSWORD` supply database-creation credentials; otherwise the MySQL credentials are used. Setup commands need permission to create databases and apply schema changes.

The platform tenant form generates a unique slug from the workspace name and suggests its domain. The local default suggests `workspace.localhost`; set `TENANT_BASE_DOMAIN=example.com` to suggest `workspace.example.com`. Domains remain editable. Tenant profiles support optional address/phone, a PNG/JPG/WebP/GIF logo up to 2 MB, and a branches flag that does not create branch records. Text and phone fields have no blanket minimum length of 5 in validation or form HTML. Logo uploads need the public storage link (`php artisan storage:link`).

Create the platform and its separate administrator, then the first tenant with its own database:

```powershell
php artisan platform:install
php artisan tenant:create
```

Commands prompt for account details and a hidden password (minimum 5 characters by default, configured by `auth.password_min_length`). Use a separate domain such as `workspace.localhost` for the local tenant; `localhost` belongs to the platform. To attach an existing tenant database/account, use `php artisan tenant:adopt` instead with that separate tenant domain; its password is preserved. Resume an unfinished setup with `php artisan tenant:retry SLUG` (add `--adopt` for an adoption). No fixed password is seeded. File sessions/cache and synchronous queues remain the development defaults.

```powershell
npm run build
php artisan serve
```

Open `http://localhost:8000/auth/login` for the platform Admin, or `http://workspace.localhost:8000/auth/login` for a registered tenant. Enabled Hospital adds an explicit Doctor choice to the existing User login; both use the unchanged `web` session guard with separate tables and unambiguous native session/remember identifiers. Without Hospital, Core retains native User login/recovery and no Doctor-table dependency. Unknown/inactive tenant hosts return 404. The root page requires authentication. Login POST uses `throttle:login`, allowing five submissions per scope/email/IP per minute. Build assets after CSS/JavaScript changes, or use `composer dev` for Laravel and Vite together. Serve only `public/`; production uses built assets and a configured web server.

## Hospital clinical entries

Appointments at `/hospital/appointments` use a compact inline form/list: `p-3` padding, a small heading, `g-2` gaps, and shorter footer spacing. Their role/plan grants and Hospital entry checks apply independently; catalog Investigation and Operation records remain shared across tenant branches.

All four clinical lists offer optional branch-scoped AJAX Doctor/Patient filters, preloading only the selected Doctor and composite Patient choice. Shared `$filterableIds` metadata maps distinct GET fields `filter_doctor_id`/`filter_patient_id` to the matching record columns, validates nullable positive IDs, and retains qualified filters across pagination/page-size changes while keeping write-field errors/old input separate, without new files or resource Request/service/provider code.

Every clinical form offers one searchable Patient ID — name — mobile selector without a separate name field, plus a button to create a Patient without leaving the page. ## Tenant table and column changes

Create a new migration for each schema change; keep already-applied files unchanged:

```powershell
php artisan make:migration add_phone_to_users_table --table=users --path=Modules/TenantCore/database/migrations
```

Define the column in that migration, then run:

```powershell
php artisan tenants:migrate
```

This updates **every registered tenant database except `deleting` tenants**, including suspended tenants. Each database tracks its own applied migrations; reruns skip completed files, and newly created tenants receive the latest schema. Shared account/permission changes belong in `Modules/Core/database/migrations/shared`; tenant-only changes belong in TenantCore. Central registry changes belong in Core's `database/migrations/central`.

The explicit local Hospital update changed the existing `2026_10_27_135801_create_operations_table.php` and `2026_10_25_171930_create_investigations_table.php` definitions without adding a migration/file. Both installed tenants were reconciled under ownership/advisory locks, converting historical integer amounts exactly by dividing by 100. Older external databases need explicit reconciliation because recorded create migrations do not rerun. Future schema changes still use new migrations; Billing's integer-minor money handling is unchanged.

Use `php artisan tenants:migrate --pretend` to preview SQL or `--tenant=ID_OR_SLUG` to select tenants (repeat for multiple). Digit-only selectors mean IDs. Production requires `--force`. Failed tenants are listed, other tenants continue and the command returns a nonzero exit code; fix the cause and rerun. There is no automatic rollback across databases. Apply populated-table changes in safe stages; never use `migrate:fresh` on real tenants. Schema work runs explicitly under a per-database lock after ownership verification, never during provider boot or an ordinary page request.

For production, configure the environment, run `composer install --no-dev --optimize-autoloader`, build assets, then run `composer optimize` for config/event/route/view caches. `composer optimize-clear` clears generated caches while preserving application-cache entries; keep ordinary development uncached. Providers and the shared asset pipeline stay lean; performance claims require repeated measurements through the HTTP runtime.
